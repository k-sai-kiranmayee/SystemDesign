Module 8 — Latest Trends

Latest LLM Architectures & Research Trends

Beyond the standard Transformer — Mixture of Experts, Mixture of Recursions, SSMs, reasoning models, test-time compute scaling, and what's next for LLMs in 2025.

1
Mixture of Experts (MoE)
Sparse activation — scale parameters without scaling compute

A dense model activates every parameter for every token. A Mixture of Experts model has multiple parallel "expert" sub-networks (FFN blocks) but only activates a small subset per token — dramatically increasing parameter count without proportional compute increase.

Dense Transformer FFN (every token uses all params):
  Token → FFN(W₁, W₂) → output    [all 4096×16384 params active]

MoE Transformer FFN (each token uses only 2 of 8 experts):
  Token → Router → scores for Expert 1..8
                    Top-2 selected: Expert 3, Expert 7
  Token → Expert3(W₁³, W₂³) ─┐
  Token → Expert7(W₁⁷, W₂⁷) ─┴→ weighted sum → output

Parameter count:  8× experts × FFN params = 8× parameters
Active params:    only 2/8 experts per token = same compute as 2× dense
Efficiency gain:  8× parameters at 2× compute cost!

Real examples:
  Mixtral 8×7B:   56B total params, 13B active per token (2 of 8 experts)
  GPT-4:          ~1.8T total params (rumoured), ~220B active (MoE)
  Grok-1:         314B total, 86B active (2 of 8 experts)
  DeepSeek-V3:    671B total, 37B active (fine-grained MoE, 256 experts)
Router / Gating
A small linear layer produces softmax scores over all experts. Top-k (usually k=2) experts are selected. Router is learned during training.
Load Balancing
Without balancing, a few experts get all tokens ("expert collapse"). Auxiliary loss penalises imbalance. Ensures all experts are used.
Expert Specialisation
Experts naturally specialise — some handle code, others prose, others math. No explicit supervision needed; emerges from training.
Using MoE models from JS — same API, different efficiencyJS
// MoE models are transparent at the API level — you call them exactly like dense models
import OpenAI from "openai";
const client = new OpenAI();

// Mixtral 8×7B via Together AI / Fireworks / Groq (faster, cheaper than GPT-4)
const together = new OpenAI({
  baseURL: "https://api.together.xyz/v1",
  apiKey:  process.env.TOGETHER_API_KEY,
});

const response = await together.chat.completions.create({
  model:    "mistralai/Mixtral-8x7B-Instruct-v0.1",
  messages: [{ role: "user", content: "Explain MoE in simple terms." }],
});

// DeepSeek-V3 (671B MoE, state-of-the-art quality at low cost)
// Available via DeepSeek API, Together, Fireworks, or self-hosted
const deepseek = new OpenAI({
  baseURL: "https://api.deepseek.com/v1",
  apiKey:  process.env.DEEPSEEK_API_KEY,
});
const r = await deepseek.chat.completions.create({
  model:    "deepseek-chat",
  messages: [{ role: "user", content: "Hello" }],
});
💡 Simple: Instead of one giant FFN that every token passes through, MoE gives each token a routing decision — "you go to Expert 3 and Expert 7". The model has 8× more parameters than an equivalent dense model but uses only 2× more compute per token, so you get a much smarter model at a lower per-token cost.
2
Mixture of Recursions (MoR)
2025 — adaptive compute depth per token via recursive layer reuse

Mixture of Recursions (Apple/MIT, 2025) is a novel architecture that combines weight sharing (sharing the same Transformer block weights across depth) with dynamic routing (a token can "recurse" through a block multiple times or skip it). Easy tokens get fewer passes; hard tokens get more.

Standard Transformer — every token passes through every layer once:
  Token → Block₁ → Block₂ → Block₃ → Block₄ → Block₅ → logits
           [L1]     [L2]     [L3]     [L4]     [L5]

Mixture of Recursions — shared weights, adaptive depth:
  All blocks share the SAME weights (W₁, W₂ — one block)
  A router decides how many times each token recurses through it

  Easy token "the":    Block → Block → logits           (2 passes)
  Medium token "runs": Block → Block → Block → logits   (3 passes)
  Hard token "∫f(x)":  Block → Block → Block → Block → Block → logits (5 passes)

  Parameters:  1 block worth of weights (memory efficient)
  Compute:     variable per token (efficient for easy inputs)
  Quality:     competitive with full depth at lower avg compute

Key papers / models:
  Universal Transformers (Dehghani 2019) — early weight-sharing
  Recursive Transformers (Apple 2024)     — predecessor
  Mixture of Recursions (2025)            — router + weight sharing combined
Weight Sharing (Tied Layers)
All "layers" use the same weight matrix. Model learns one powerful transformation applied repeatedly. Memory = 1 layer, expressiveness grows with recursion depth.
Dynamic Routing
A lightweight router scores each token at each iteration. High-confidence tokens exit early. Ambiguous/complex tokens get more iterations. Budget can be set at inference time.
MoR vs MoE comparison:
  MoE: same depth, more width (more experts, but each used once)
  MoR: same width, variable depth (one expert, used multiple times)

  They can be COMBINED: each "expert" in MoE can itself be a recursive block.
  This is the direction of next-gen architectures (Recursive MoE).
💡 Simple: MoR asks: why give a space character the same compute as a complex equation? One shared block's weights are reused recursively — simple tokens exit after 1 pass, complex ones get up to R passes. The model becomes deep when needed and shallow when not, using far fewer total FLOPs. Still research-only in 2025, but a compelling direction.
3
State Space Models — Mamba & RWKV
Linear-time sequence modelling — replacing quadratic attention

Standard attention is O(n²) — doubling sequence length quadruples cost. State Space Models (SSMs) achieve O(n) linear complexity by maintaining a compact hidden state, making them dramatically faster for long sequences.

Transformer Attention (quadratic):
  Every token attends to every other token.
  Sequence 1K tokens:    1M operations
  Sequence 100K tokens:  10B operations  ← 10,000× slower

Mamba (linear via selective SSM):
  Maintains a fixed-size hidden state h that is updated token by token.
  Key innovation: SELECTIVE state spaces — Δ, B, C matrices are input-dependent
  (unlike old S4 models which had fixed parameters)
  Sequence 1K tokens:    1K operations
  Sequence 100K tokens:  100K operations  ← scales linearly!

  State update:  h_t = A·h_{t-1} + B·x_t
  Output:        y_t = C·h_t

RWKV (Receptance Weighted Key Value):
  Combines RNN-style recurrence with attention-like expressiveness
  Inference: O(1) per token (constant memory, no KV cache growth)
  Training:  parallelisable like Transformer via WKV kernel

Hybrid (best of both worlds):
  Jamba (AI21):  Mamba + Transformer layers interleaved
  Zamba:         SSM backbone + sparse attention every N layers
  → Near-Mamba efficiency with Transformer-quality long-range reasoning
Running Mamba models via Transformers.js / HF Inference APIJS
// Mamba models are available on HF Hub and usable via the standard Inference API
import { HfInference } from "@huggingface/inference";
const hf = new HfInference(process.env.HF_TOKEN);

// Mamba-2 — linear attention model
const result = await hf.textGeneration({
  model:  "state-spaces/mamba-2.8b-hf",
  inputs: "The key advantage of Mamba over Transformers is",
  parameters: { max_new_tokens: 100, temperature: 0.7 },
});

// RWKV — runs efficiently even at 100K+ tokens
const rwkv = await hf.textGeneration({
  model:  "RWKV/rwkv-6-world-7b",
  inputs: "Long document text here...",
  parameters: { max_new_tokens: 500 },
});
💡 Simple: Standard attention stores and reads an n×n matrix in memory — cost explodes at 32K+ tokens. Mamba compresses all past context into a fixed-size hidden state and updates it in O(1) per token. Perfect for streaming tasks (audio, genomics, real-time feeds) where you do not need to recall arbitrary past tokens precisely.

Reasoning Models & Test-Time Compute Scaling
o1 · o3 · DeepSeek-R1 · QwQ — think longer, answer better

Standard LLMs improve by training more. Reasoning models improve at inference time — they generate a long internal chain of thought before answering. Trading compute for quality at inference time is the key new paradigm.

Standard model (fast, single pass):
  User: "Prove that √2 is irrational"
  Model: [one forward pass] → answer (may be wrong)

Reasoning model (think longer → better answer):
  User: "Prove that √2 is irrational"
  <think>
    Let me assume √2 = p/q in lowest terms...
    Then 2 = p²/q², so p² = 2q², so p² is even...
    Therefore p is even. Let p = 2k. Then 4k² = 2q²...
    So q² = 2k², meaning q is also even...
    But p/q in lowest terms can't both be even. Contradiction!
  </think>
  "Proof by contradiction: assume √2 = p/q in lowest terms..."

Test-Time Compute Scaling Law (Snell et al. 2024):
  More inference compute → better answers, following a power law
  Similar to how more training compute → smarter models (Chinchilla law)
  Key insight: for hard problems, it's more efficient to "think more"
               than to use a bigger model that "thinks once"

Models:
  OpenAI o1 / o3:     internal CoT, RLVR training (RL with verifiable rewards)
  DeepSeek-R1:        open-source, 671B MoE + reasoning, matches o1
  QwQ-32B (Qwen):     32B reasoning model, open-source, near o1 quality
  Claude 3.7 Sonnet:  extended thinking mode (variable compute budget)
Calling reasoning models from JSJS
// OpenAI o3-mini — set reasoning_effort: "low" | "medium" | "high"
import OpenAI from "openai";
const client = new OpenAI();

const o3Response = await client.chat.completions.create({
  model:            "o3-mini",
  reasoning_effort: "high",   // more thinking tokens = better quality, higher cost
  messages: [{ role: "user", content: "Prove that √2 is irrational." }],
});

// Claude 3.7 Sonnet — extended thinking (budget_tokens controls thinking depth)
import Anthropic from "@anthropic-ai/sdk";
const anthropic = new Anthropic();

const claudeResponse = await anthropic.messages.create({
  model:      "claude-3-7-sonnet-20250219",
  max_tokens: 16000,
  thinking: { type: "enabled", budget_tokens: 10000 },  // up to 10k thinking tokens
  messages: [{ role: "user", content: "Solve this step by step: ..." }],
});
// Response includes thinking blocks + final answer block
const thinking = claudeResponse.content.find(b => b.type === "thinking");
const answer   = claudeResponse.content.find(b => b.type === "text");

// DeepSeek-R1 (open-source, reasoning model) via Together AI
const together = new OpenAI({ baseURL: "https://api.together.xyz/v1", apiKey: process.env.TOGETHER_API_KEY });
const r1 = await together.chat.completions.create({
  model:    "deepseek-ai/DeepSeek-R1",
  messages: [{ role: "user", content: "Prove that √2 is irrational." }],
});
💡 Simple: Standard LLMs go prompt → answer immediately. Reasoning models go prompt → extended thinking (2,000–50,000 tokens of internal dialogue) → answer. The thinking is expensive but unlocks skills that are impossible without it — like solving AIME math problems or generating correct multi-file code changes. Spend more tokens thinking = better answer, without training a bigger model.

Small Language Models (SLMs)
Phi · Qwen · Llama 3.2 1B — GPT-4 quality tasks on edge hardware

2024–2025 showed that careful data curation and training recipes can produce small models (<10B params) that beat older large models on many tasks. SLMs enable on-device AI, lower cost, faster inference, and privacy.

SLM Leaderboard (approximate, task-dependent):
  Model           Size   Context  Runs on        Key strength
  ─────────────────────────────────────────────────────────────
  Phi-3.5-mini    3.8B   128K     laptop CPU     Data quality focus (textbooks)
  Phi-4           14B    16K      1× RTX 4090    STEM, reasoning, outperforms GPT-3.5
  Qwen2.5-7B      7B     128K     1× RTX 3080    Coding, multilingual, math
  Qwen2.5-Coder   7B     128K     1× RTX 3080    Best-in-class code generation at 7B
  Llama-3.2-1B    1B     128K     phone / Pi     On-device, offline capable
  Llama-3.2-3B    3B     128K     laptop         Strong general purpose at 3B
  Gemma-2-9B      9B     8K       1× GPU         Google quality, open weights
  SmolLM2-1.7B    1.7B   8K       browser (WASM) Designed for Transformers.js

Key insight: "Less but better data" > "more data"
  Phi models trained on synthetic "textbook quality" data
  outperform models 10× their size on reasoning benchmarks.
SLMs in the browser with Transformers.jsJS
// Run entirely in the browser — no server, no API key, works offline
// npm install @xenova/transformers  (or use CDN)
import { pipeline } from "https://cdn.jsdelivr.net/npm/@xenova/transformers@2.17.2";

// SmolLM2 — designed for browser inference
const generator = await pipeline("text-generation", "HuggingFaceTB/SmolLM2-360M-Instruct");

// Stream tokens to the DOM in real-time
const output = await generator(
  [{ role: "user", content: "Summarise the Eiffel Tower in 2 sentences." }],
  {
    max_new_tokens: 100,
    callback_function: (x) => {
      document.getElementById("output").textContent += x[0].output_token_ids ?? "";
    },
  }
);
💡 Simple: A fine-tuned 3.8B model on a specific task often matches or beats a generic 70B model — and it runs on a phone. Phi-3.5 Mini achieves GPT-3.5-level quality because it was trained on extremely curated textbook-quality data rather than just raw internet dumps. Quality of training data beats quantity of parameters for narrow domains.

Multi-modal Models — Vision, Audio & Beyond
GPT-4o · Claude 3.5 · Gemini 1.5 — unified models across modalities
Modality Stack (2025):

  Text  ──┐
  Image ──┤──▶ Encoder ──▶ Shared Embedding Space ──▶ LLM Backbone ──▶ Text / Image / Audio out
  Audio ──┘

Architecture approaches:
  1. Adapter-based: freeze LLM + add modality-specific encoder + lightweight adapter
     (LLaVA, BLIP-2, InstructBLIP)
  2. Natively multi-modal: train unified model from scratch on all modalities
     (GPT-4o, Gemini 1.5, Claude 3.5 Sonnet)
  3. Any-to-any: generate images, audio, video natively (not just text)
     (GPT-4o with image gen, Gemini Ultra)

Vision capabilities maturity:
  ✅ Image captioning, VQA        — production-ready
  ✅ Document / PDF understanding — production-ready
  ✅ Chart / diagram analysis     — production-ready
  ⚠️ Fine-grained OCR             — improving
  ⚠️ Video understanding          — limited context, improving
  🔬 Real-time vision + action    — research / early products
Vision API — image + text from JSJS
import OpenAI from "openai";
import fs     from "fs";

const client = new OpenAI();

// Option A: URL
const response = await client.chat.completions.create({
  model:    "gpt-4o",
  messages: [{
    role: "user",
    content: [
      { type: "text",      text: "What does this chart show?" },
      { type: "image_url", image_url: { url: "https://example.com/chart.png" } },
    ],
  }],
});

// Option B: Base64 local file
const imageData = fs.readFileSync("./chart.png").toString("base64");
const r2 = await client.chat.completions.create({
  model:    "gpt-4o",
  messages: [{
    role: "user",
    content: [
      { type: "text",      text: "Extract all data from this chart as JSON." },
      { type: "image_url", image_url: { url: `data:image/png;base64,${imageData}` } },
    ],
  }],
  response_format: { type: "json_object" },
});
💡 Simple: Vision models tile your image into patches and treat each patch like a token. Sending one 1024×1024 image costs ~1700 tokens. In a JS app, you include an image_url or base64 string in the messages array and the model reasons over text and image together in one forward pass — no separate vision pipeline needed.

Attention Efficiency Innovations
FlashAttention · Sliding Window · Ring Attention · Speculative Decoding
FlashAttention 2 / 3
Tiled, memory-efficient attention kernel. Avoids materialising full n×n attention matrix in HBM. 2–8× faster than standard attention. Used in all modern LLM training/inference. Transparent to API users.
Sliding Window Attention
Each token only attends to a local window (e.g., last 4K tokens) instead of full context. Used in Mistral, Phi. Reduces memory from O(n²) to O(n×window). Some global attention layers mix in for coherence.
Ring Attention
Distribute long-context attention across multiple GPUs in a ring. Each GPU handles a chunk; activations passed around the ring. Enables 1M+ token contexts across a GPU cluster.
Speculative Decoding
Small draft model proposes K tokens. Large model verifies all K in one forward pass (K× faster). If tokens accepted, great. If rejected, large model corrects from that point. Used in Gemini, Claude.
Speculative Decoding (2–4× inference speedup):

  Draft model (small, fast) proposes 4 tokens:
    "The sky is blue"

  Target model (large, slow) verifies ALL 4 in one pass:
    P("The") = 0.98 ✅   P("sky"|"The") = 0.87 ✅
    P("is"|"The sky") = 0.92 ✅   P("blue"|...) = 0.63 ✅  all accepted!

  Without speculative decoding: 4 separate large model forward passes
  With speculative decoding:    1 large model pass to validate all 4
  Speedup:                      ~3–4× for compatible prompts

KV Cache Improvements (2024-2025):
  PagedAttention (vLLM):  page-based memory for KV cache, eliminates fragmentation
  RadixAttention:         tree-based prefix sharing across multiple requests
  MLA (Multi-head Latent Attention, DeepSeek):  compress KV cache via low-rank projection
💡 Simple: FlashAttention rewrites attention computation to stay inside the GPU's fast SRAM cache instead of repeatedly writing to slow HBM memory. Same mathematical result, 2–4× faster, 1000× less memory traffic at long contexts. It is now the default in every serious inference stack and is enabled automatically in PyTorch SDPA.

Modern Alignment — GRPO, RLVR & Constitutional AI
Beyond RLHF: scalable, stable reinforcement learning for LLMs
GRPO (Group Relative Policy Optimisation — DeepSeek 2024):
  Like PPO but without a separate value/critic model.
  For each prompt, sample G outputs, compute rewards, normalise within the group.
  Policy gradient uses relative advantage (how much better than the group average).

  G outputs from model → reward model scores each → normalise → gradient update
  Key win: no value model = 50% fewer parameters to train = much more memory efficient

RLVR (Reinforcement Learning with Verifiable Rewards):
  Used by o1, DeepSeek-R1. Instead of a learned reward model, use HARD rewards:
  ✅ Math: check if answer equals ground truth
  ✅ Code: run tests — pass/fail
  ✅ Logic: formal verifier
  → Much more reliable than "does a reward model like this?"
  → Models trained with RLVR spontaneously develop chain-of-thought reasoning

Constitutional AI (Anthropic):
  Stage 1: SFT on human feedback
  Stage 2: Model critiques its own outputs against a "constitution" (list of principles)
  Stage 3: RLAIF — AI-generated preference data replaces human annotators at scale
  → Enables scalable alignment without massive human labelling cost

Process Reward Models (PRM):
  Traditional reward model: score the FINAL answer (outcome reward)
  PRM: score each STEP of reasoning separately
  → Catches reasoning errors early, much better for math/logic
  → OpenAI Math-Shepherd, DeepSeek-PRM
💡 Simple: GRPO and RLVR train the model by generating multiple answers to the same question, then rewarding only the verifiably correct ones. No human labellers, no reward model — just check whether the math answer matches. This created DeepSeek-R1's reasoning capability. Constitutional AI generates its own training critiques using a written set of principles, removing human labelling from alignment entirely.

Edge Cases & Practical Gotchas
What trips up JS developers using cutting-edge models
HIGH
💸
Reasoning Model Cost Shock
o3 with reasoning_effort:"high" can use 100k+ thinking tokens per request. At $15/M tokens, a single hard question can cost $1.50. Production apps can rack up $1000s/day unexpectedly.
Cap thinking tokens (budget_tokens in Claude). Use "low" effort for routing/classification. Only use "high" for genuinely hard tasks. Monitor usage in real-time.
HIGH
🔄
MoE Expert Load Imbalance at Inference
During fine-tuning on narrow domains, MoE models can develop "dead experts" — some experts get no tokens, losing capacity. Model quality degrades selectively.
Verify expert utilisation metrics during SFT. Mix domain data with general data. Use existing well-trained MoE checkpoints rather than fine-tuning MoE from scratch.
MED
🔁
MoR Infinite Recursion
Mixture of Recursions with a poorly calibrated router can loop the same block excessively for "uncertain" tokens, stalling inference with no output.
Always set a max_iterations cap. Monitor per-token iteration counts during inference. MoR models should have a hard exit gate.
MED
📏
SSM Long-Context Degradation
Mamba/RWKV compress history into a fixed-size state. For very long sequences, old information can be "forgotten" if newer tokens compress it out. Unlike transformers which always can attend back.
For recall-heavy tasks (exact lookup in 100K doc), prefer Transformer-based long-context models. Use Mamba for tasks where recent context dominates.
MED
👁️
Vision Token Cost
A 1024×1024 image tiles to ~1700 tokens (GPT-4o). Sending 10 images per request = 17,000 tokens just for images. Costs multiply fast in document processing pipelines.
Downscale images before sending (detail:"low" = 85 tokens flat). Only send relevant crops. Cache vision embeddings for repeated analysis of the same image.
LOW
⏳
Speculative Decoding Latency Regression
If the draft model frequently gets rejected (cold prompts, unusual domains), the overhead of running the draft model adds latency without benefit.
Speculative decoding works best with aligned draft+target model families. Domain mismatch between draft and target degrades acceptance rate. Use standard decoding for low-temperature, high-rejection scenarios.
💡 Simple: The recurring theme across all 2025 trends: every technique has a trade-off. MoE needs all experts loaded in VRAM. Reasoning models are 100× more expensive than standard models for simple queries. SSMs lose precise long-range recall. SLMs underperform on genuinely novel tasks. Match the technique to the constraint — there is no universal winner.
