Module 4 — RAG & LangChain

Retrieval-Augmented Generation & LCEL

Overcome LLM knowledge cutoffs and hallucination with vector stores, document retrieval, LangChain chains, and RAGAS evaluation. Builds on Module 3 API patterns; used by Module 5 Agents.

1
LLM Limitations — Why RAG Exists
Knowledge cutoff · Hallucination · Context constraints
📅
Knowledge Cutoff
Training data has a fixed end date. GPT-4 knows nothing about events after April 2023. You cannot ask it about last week's news or your internal docs.
🎭
Hallucination
LLMs generate plausible-sounding text even when they don't know the answer. They confidently fabricate citations, statistics, and facts.
📏
Context Window Limit
Even 128k-token windows can't hold an entire knowledge base. You must selectively retrieve what's relevant instead of stuffing everything in.
🔒
Private / Proprietary Data
Your internal Confluence, Jira, codebase, or customer data was never in training data. Fine-tuning is expensive; retrieval is cheaper and fresher.
⚖️
Reasoning Gaps
LLMs struggle with multi-step arithmetic, latest API specs, and exact facts. Grounding with retrieved evidence dramatically reduces errors.
🔄
Stale Fine-Tuned Models
Fine-tuning encodes knowledge statically. Updates require re-training. RAG lets you update the knowledge base without touching the model.
LLM ALONE:
  User: "What is our Q3 revenue?"
  LLM:  "I don't have access to your financial data." (honest)
         or "Your Q3 revenue was $14.2M" (hallucinated — dangerous)

LLM + RAG:
  User: "What is our Q3 revenue?"
  Retrieval: fetch relevant docs from your vector DB
  LLM:  "According to the Q3 earnings report (retrieved), revenue was $14.2M"
         Source: [finance/q3-2024.pdf, page 4]  ← citable, verifiable
💡 Simple: LLMs are frozen at their training cutoff and cannot see your private data. RAG fixes this by fetching relevant documents at query time and passing them to the model as context — like an open-book exam instead of closed-book. The model's job becomes "answer using these specific paragraphs", which is far more reliable than relying on memorised training data.

RAG Architecture — End to End
Indexing pipeline + Query pipeline
═══════════════════════════════ INDEXING PIPELINE (offline) ═══════════════════════════════

  Raw Documents              Load              Chunk              Embed              Store
  ┌───────────┐           ┌────────┐        ┌────────┐        ┌────────┐        ┌────────┐
  │ PDF / MD  │──────────▶│Loaders │───────▶│Splitter│───────▶│Embed   │───────▶│Vector  │
  │ HTML / DB │           │        │        │        │        │Model   │        │Store   │
  │ CSV / API │           └────────┘        └────────┘        └────────┘        └────────┘
  └───────────┘         (DocLoader)       (TextSplitter)   (OpenAI/local)   (Chroma/FAISS)

═══════════════════════════════ QUERY PIPELINE (online) ═══════════════════════════════════

  User Query
      │
      ▼
  ┌──────────┐    embed     ┌──────────┐   top-k    ┌──────────┐
  │  Query   │─────────────▶│  Vector  │───────────▶│Retrieved │
  │  Text    │              │  Store   │            │  Chunks  │
  └──────────┘              └──────────┘            └──────────┘
                                                         │
                              ┌──────────────────────────┘
                              │  Build prompt:
                              │  [System] You are a helpful assistant.
                              │  [Context] {retrieved chunks}
                              │  [User] {original query}
                              ▼
                         ┌──────────┐
                         │   LLM    │──────▶  Final Answer + Citations
                         └──────────┘

Two distinct phases: Indexing (done once / periodically) converts your documents into searchable embeddings. Querying (every user request) retrieves relevant chunks and passes them to the LLM as context.

🔍 What the "Embed Model" box actually does:

The embed step in both pipelines is not a simple lookup — it is a full encoder Transformer forward pass (e.g., BERT-base, text-embedding-ada-002, all-MiniLM-L6-v2):

text chunk / query
  ↓ Tokenizer (of the embedding model)
Token IDs
  ↓ Static token lookup + positional encoding
Token vectors
  ↓ Bidirectional self-attention × N layers ← full Transformer Architecture
Contextual token vectors
  ↓ Pool ([CLS] token or mean pool all tokens)
Single fixed-size vector [384 / 768 / 1536-dim] → stored in vector DB

This is completely separate from the LLM's internal token embedding lookup. The encoder uses bidirectional attention (sees all tokens simultaneously) vs the LLM decoder which uses causal attention (sees only past tokens). Both the indexing and querying steps must use the same embedding model — they must live in the same vector space for cosine similarity to be meaningful.

💡 Simple: Two phases: indexing (one-time setup — split docs into chunks, run each chunk through an encoder Transformer to get a vector, store in a vector database) and querying (per request — run the question through the same encoder, find matching chunk vectors, pass the text to the LLM). The embed step is a full Transformer forward pass, not just a lookup table.

Document Loading & Chunking Strategies
The quality of retrieval starts here

LangChain Document Loaders:

Document Loaders (LangChain JS)JS
import { PDFLoader }          from "@langchain/community/document_loaders/fs/pdf";
import { CheerioWebBaseLoader } from "@langchain/community/document_loaders/web/cheerio";
import { CSVLoader }           from "@langchain/community/document_loaders/fs/csv";
import { NotionLoader }        from "@langchain/community/document_loaders/fs/notion";

// PDF — loads each page as a Document
const pdfLoader = new PDFLoader("./docs/report.pdf");
const pdfDocs   = await pdfLoader.load();
// [{ pageContent: "...", metadata: { source, pdf: { page } } }, ...]

// Web page — HTML → text via Cheerio
const webLoader = new CheerioWebBaseLoader("https://example.com/docs");
const webDocs   = await webLoader.load();

// Each Document has: { pageContent: string, metadata: Record<string,any> }

Chunking strategies — choosing the right one matters:

StrategyHow it worksBest forPitfall

Recursive characterTry splitting on \n\n, \n, " " in order; keep chunks ≤ N charsMost text documents (recommended default)Still not semantics-aware

RecursiveCharacterTextSplitter (LangChain JS)JS
import { RecursiveCharacterTextSplitter } from "langchain/text_splitter";

const splitter = new RecursiveCharacterTextSplitter({
  chunkSize:    1000,   // max characters per chunk
  chunkOverlap: 200,    // overlap to preserve context across boundaries
  separators: ["\n\n", "\n", " ", ""],  // tries these in order
});

const chunks = await splitter.splitDocuments(pdfDocs);
// Returns Document[] — each chunk preserves metadata from parent
console.log(chunks[0]);
// { pageContent: "...1000 chars...", metadata: { source: "report.pdf", loc: { ... } } }
chunkOverlap = 200 example:

Original text: [============================== 2000 chars ==============================]

Chunk 1:        [==== 1000 ====]
Chunk 2:              [===200===][==== 800 ====]
Chunk 3:                               [===200===][==== 800 ====]

The 200-char overlap means a sentence cut at a boundary still appears
in the next chunk — ensuring retrieval can find the full thought.
💡 Simple: Chunking is the art of cutting documents into searchable pieces. Too small loses surrounding context; too large includes irrelevant content. Overlapping windows (e.g. 200-char overlap) prevent important sentences from being split across boundaries and getting lost during retrieval.

Embeddings & Vector Stores
Semantic search infrastructure

An embedding converts text into a dense numerical vector (e.g., 1536 dims for OpenAI ada-002) such that semantically similar texts have high cosine similarity. Vector stores index these vectors for fast approximate nearest-neighbour (ANN) search.

⚠️ RAG embeddings ≠ LLM's internal token embeddings — they are fundamentally different:
PropertyRAG chunk embeddingLLM token embedding (internal)
Produced byEncoder Transformer — full bidirectional forward passStatic weight matrix lookup — zero computation
Context-aware?✅ Yes — all tokens see each other❌ No — context-free, fixed per token ID
GranularityOne vector per document chunk (pooled)One vector per sub-word token
Typical dimension384 / 768 / 1536d_model of the LLM — 768 to 4096+
PurposeSemantic similarity search — find relevant chunksConvert token IDs → float space for TA to process
Stored externally?Yes — persisted in vector DBNo — computed per LLM forward pass, ephemeral

"dog bites man"  → [0.12, -0.43, 0.87, ..., 0.22]
"man bit by dog" → [0.11, -0.44, 0.85, ..., 0.23]  ← similar!
"quantum physics" → [0.93,  0.12, -0.54, ..., -0.67]  ← distant

cosine_similarity("dog bites man", "man bit by dog") ≈ 0.97
cosine_similarity("dog bites man", "quantum physics") ≈ 0.12

Embeddings + Chroma (LangChain JS)JS
import { OpenAIEmbeddings }   from "@langchain/openai";
import { Chroma }             from "@langchain/community/vectorstores/chroma";

const embeddings = new OpenAIEmbeddings({ model: "text-embedding-3-small" });

// ── Index (done once) ──────────────────────────────────────────────────
const vectorStore = await Chroma.fromDocuments(
  chunks,       // Document[] from splitter
  embeddings,
  { collectionName: "my-docs", url: "http://localhost:8000" }
);

// ── Query (every request) ─────────────────────────────────────────────
const retriever = vectorStore.asRetriever({ k: 5 });  // top-5 chunks

const relevantDocs = await retriever.invoke("What is our refund policy?");
// relevantDocs: Document[] — top-5 most similar chunks

// Similarity search with score (distance)
const withScores = await vectorStore.similaritySearchWithScore(
  "refund policy", 3
);
// [[doc, 0.87], [doc, 0.81], [doc, 0.74]]
💡 Simple: A vector store is a semantic search engine. You turn each chunk into a number array (embedding) and store it. At query time, you turn the question into a number array and find the chunks whose arrays are mathematically closest — this finds conceptually similar text without needing exact keyword matches.

LangChain & LCEL
LangChain Expression Language — composable chains via the pipe operator

LCEL (LangChain Expression Language) uses the | pipe operator to compose Runnables — anything that implements .invoke(), .stream(), and .batch(). The result is a composable, streamable, parallelizable chain.

LCEL Runnable Interface:
  invoke(input)  → output           (single call)
  stream(input)  → AsyncIterator    (streaming tokens)
  batch([...])   → output[]         (parallel calls)

LCEL Pipe:
  chain = A | B | C
  chain.invoke(x)  ≡  C.invoke(B.invoke(A.invoke(x)))

Core Runnables:
  PromptTemplate    → formats a string using variables
  ChatOpenAI        → sends messages to OpenAI, returns AIMessage
  StrOutputParser   → extracts .content string from AIMessage
  RunnablePassthrough → passes input through unchanged (useful for merging)
  RunnableParallel  → runs multiple runnables in parallel, merges outputs
LCEL — Basic ChainJS
import { ChatOpenAI }         from "@langchain/openai";
import { PromptTemplate }     from "@langchain/core/prompts";
import { StrOutputParser }    from "@langchain/core/output_parsers";

const prompt = PromptTemplate.fromTemplate(
  "Answer the following question: {question}"
);

const model  = new ChatOpenAI({ model: "gpt-4o-mini", temperature: 0 });
const parser = new StrOutputParser();

const chain  = prompt | model | parser;  // LCEL pipe

const result = await chain.invoke({ question: "What is 2+2?" });
// "4"

// Streaming
for await (const chunk of await chain.stream({ question: "What is 2+2?" })) {
  process.stdout.write(chunk);
}
LCEL — Full RAG ChainJS
import { RunnablePassthrough, RunnableSequence } from "@langchain/core/runnables";
import { ChatPromptTemplate } from "@langchain/core/prompts";

const ragPrompt = ChatPromptTemplate.fromMessages([
  ["system", "You are a helpful assistant. Use ONLY the context below.\n\nContext:\n{context}"],
  ["human",  "{question}"],
]);

// Format retrieved docs into a single string
const formatDocs = (docs) => docs.map(d => d.pageContent).join("\n\n");

const ragChain = RunnableSequence.from([
  {
    context:  retriever.pipe(formatDocs),  // retrieve → format
    question: new RunnablePassthrough(),    // pass question through
  },
  ragPrompt,
  model,
  parser,
]);

const answer = await ragChain.invoke("What is our refund policy?");
console.log(answer);  // grounded answer from retrieved docs
💡 Simple: LCEL is LangChain's pipe operator for connecting steps: prompt | llm | parser. Each component's output becomes the next one's input. The full RAG chain is just two connected components — retriever and generator — replacing pages of boilerplate glue code.

Prompts & Output Parsers
Structured prompt templates and typed outputs

Prompt Template Types:

  • PromptTemplate: single string with {variables}
  • ChatPromptTemplate: list of (role, template) pairs for chat models
  • FewShotPromptTemplate: dynamically inserts examples from an example selector
  • MessagesPlaceholder: inserts a list of messages (e.g., chat history)

Output Parser Types:

  • StrOutputParser: extracts .content as plain string
  • JsonOutputParser: parses model JSON response into JS object
  • StructuredOutputParser: validates JSON against a Zod schema
  • CommaSeparatedListOutputParser: splits comma-delimited text into array
Structured Output with ZodJS
import { z }                      from "zod";
import { StructuredOutputParser }  from "langchain/output_parsers";
import { ChatPromptTemplate }      from "@langchain/core/prompts";

const schema = z.object({
  sentiment: z.enum(["positive", "negative", "neutral"]),
  confidence: z.number().min(0).max(1),
  reasons: z.array(z.string()),
});

const outputParser = StructuredOutputParser.fromZodSchema(schema);

const prompt = ChatPromptTemplate.fromMessages([
  ["system", "Analyse the sentiment.\n{format_instructions}"],
  ["human", "{text}"],
]);

const chain = prompt | model | outputParser;

const result = await chain.invoke({
  text: "I love this product but shipping was slow.",
  format_instructions: outputParser.getFormatInstructions(),
});
// { sentiment: "positive", confidence: 0.72, reasons: ["loves product", "slow shipping"] }
💡 Simple: Output parsers bridge free-text LLM responses and the structured data your app needs. Instead of fragile regex on "The sentiment is positive, confidence 72%", you define a schema (Zod or similar) and LangChain ensures the response is parsed into it — plus automatically retries if the format is wrong.

Advanced Retrieval Strategies
MMR · Hybrid BM25+vector · Multi-query · Self-query
MMR (Maximal Marginal Relevance)
Fetches top-k docs but re-ranks to reduce redundancy. Returns diverse results — relevant AND different from each other. Set lambda: 0=max diversity, 1=max relevance.
Hybrid BM25 + Vector
BM25 = keyword matching (exact terms). Vector = semantic matching. Combine scores with RRF (Reciprocal Rank Fusion). Catches both exact product codes and paraphrased questions.
Multi-Query Retrieval
LLM rephrases the query 3–5 ways → run each retrieval → deduplicate union. Overcomes retrieval misses caused by specific wording.
Self-Query Retrieval
LLM extracts structured filters from natural language. "Show me docs from 2024 tagged 'finance'" → filter: {year:2024, tag:'finance'} + semantic search.
MMR Retriever + Multi-Query RetrieverJS
import { MultiQueryRetriever }  from "langchain/retrievers/multi_query";

// MMR — diversity-aware retrieval
const mmrRetriever = vectorStore.asRetriever({
  searchType: "mmr",
  searchKwargs: { fetchK: 20, lambda: 0.5 },  // fetch 20, return 5
  k: 5,
});

// Multi-Query — rephrase question multiple ways then union results
const mqRetriever = MultiQueryRetriever.fromLLM({
  llm:       model,
  retriever: vectorStore.asRetriever({ k: 5 }),
  verbose:   true,   // logs generated sub-queries
});

const docs = await mqRetriever.invoke("How does billing work for enterprise?");
// Internally generates:
//  "enterprise billing model"
//  "how are enterprise customers charged"
//  "pricing structure for large companies"
// → runs all 3 retrievals → deduplicates → returns union
💡 Simple: Basic cosine search returns the K most similar chunks — but they may all say the same thing. MMR adds diversity by penalising redundant results. Multi-query generates alternative phrasings of your question to catch documents that use different vocabulary for the same concept. These two additions alone give 15–25% quality improvement.

Conversational RAG with Chat History
Multi-turn context-aware retrieval
Problem with naive RAG in conversations:
  Turn 1: "What is the refund policy?"         → retrieval works fine
  Turn 2: "How long does IT take?"             → "it" = refund? shipping? unclear
                                               → semantic search on "it" → wrong results

Solution: Contextualise the query first:
  Turn 2 → LLM rephrases → "How long does the refund process take?" → retrieval → answer

  ┌────────────┐    ┌────────────────┐    ┌────────────┐    ┌─────┐    ┌──────┐
  │Chat History│───▶│ Contextualise  │───▶│  Retrieve  │───▶│ RAG │───▶│Reply │
  │+ New Query │    │ Query LLM call │    │  (vector)  │    │chain│    │      │
  └────────────┘    └────────────────┘    └────────────┘    └─────┘    └──────┘
Conversational RAG ChainJS
import { createHistoryAwareRetriever }     from "langchain/chains/history_aware_retriever";
import { createRetrievalChain }            from "langchain/chains/retrieval";
import { createStuffDocumentsChain }       from "langchain/chains/combine_documents";
import { MessagesPlaceholder }             from "@langchain/core/prompts";
import { HumanMessage, AIMessage }         from "@langchain/core/messages";

// Step 1: Contextualise the user query given chat history
const contextualisePrompt = ChatPromptTemplate.fromMessages([
  ["system", "Given the chat history and the latest user question, reformulate it as a standalone question."],
  new MessagesPlaceholder("chat_history"),
  ["human", "{input}"],
]);
const historyAwareRetriever = await createHistoryAwareRetriever({
  llm: model, retriever, rephrasePrompt: contextualisePrompt,
});

// Step 2: QA prompt with context
const qaPrompt = ChatPromptTemplate.fromMessages([
  ["system", "Answer using the context below.\n\n{context}"],
  new MessagesPlaceholder("chat_history"),
  ["human", "{input}"],
]);
const qaChain     = await createStuffDocumentsChain({ llm: model, prompt: qaPrompt });
const ragChain    = await createRetrievalChain({ retriever: historyAwareRetriever, combineDocsChain: qaChain });

// Usage
const chatHistory = [];
const q1 = await ragChain.invoke({ input: "What is the refund policy?", chat_history: chatHistory });
chatHistory.push(new HumanMessage("What is the refund policy?"), new AIMessage(q1.answer));

const q2 = await ragChain.invoke({ input: "How long does it take?", chat_history: chatHistory });
// "it" is contextualised → "How long does the refund process take?"
💡 Simple: Standard RAG treats every question in isolation. Conversational RAG first rewrites the question to be self-contained given the chat history, then retrieves. That is why a follow-up "How long does it take?" correctly becomes "How long does the refund process take?" — the model understands the pronoun from context.

Evaluating RAG — RAGAS Metrics
Quantify retrieval quality and answer faithfulness
RAGAS Evaluation Framework:

  Given: { question, answer, context[], ground_truth }

  ┌──────────────────────────────────────────────────────────────────────┐
  │  Metric               What it measures           Range  Target       │
  ├──────────────────────────────────────────────────────────────────────┤
  │  Faithfulness         Is the answer supported     0–1    > 0.8       │
  │                       by the retrieved context?                      │
  │  Answer Relevance     Is the answer relevant       0–1    > 0.8       │
  │                       to the question?                               │
  │  Context Recall       Are all necessary facts      0–1    > 0.7       │
  │                       in the retrieved context?                      │
  │  Context Precision    Are retrieved docs actually  0–1    > 0.7       │
  │                       needed? (no noise)                             │
  │  Answer Correctness   Is the answer factually      0–1    > 0.7       │
  │                       correct vs ground truth?                       │
  └──────────────────────────────────────────────────────────────────────┘

  Faithfulness LOW  → LLM hallucinating beyond the context
  Context Recall LOW → Retriever missing important chunks
  Context Precision LOW → Too many irrelevant chunks polluting the prompt
LangSmith Evaluation — JS-native RAG evaluationJS
// npm install langsmith  (also see Module 6 for full LangSmith setup)
// LANGCHAIN_TRACING_V2=true  LANGCHAIN_API_KEY=lsv2_pt_xxx  LANGCHAIN_PROJECT=rag-eval
import { evaluate }   from "langsmith/evaluation";
import { Client }     from "langsmith";

const client = new Client();

// Target: the RAG chain to evaluate
const target = (input) => ragChain.invoke(input.question);

// Custom evaluators (mirroring RAGAS metrics)
const faithfulnessEval = async ({ inputs, outputs }) => {
  // Use an LLM judge to check if the answer is grounded in the retrieved context
  const judgment = await llmJudge.invoke(
    `Context: ${outputs.context}\nAnswer: ${outputs.answer}\nIs the answer fully supported by the context? Reply YES or NO.`
  );
  return { key: "faithfulness", score: judgment.content.includes("YES") ? 1 : 0 };
};

const exactMatch = ({ outputs, referenceOutputs }) =>
  ({ key: "exact_match", score: outputs.answer === referenceOutputs.answer ? 1 : 0 });

const result = await evaluate(target, {
  data:             "rag-golden-dataset",  // dataset name in LangSmith
  evaluators:       [faithfulnessEval, exactMatch],
  experimentPrefix: "rag-v2",
  maxConcurrency:   4,
});
// Results visible in LangSmith UI: Experiments → rag-v2
// { faithfulness: 0.92, exact_match: 0.78 }

Improving low RAGAS scores:

Low metricRoot causeFix
FaithfulnessLLM adds info not in contextStricter system prompt ("ONLY use context"), temperature=0
Context RecallRelevant chunks not retrievedIncrease k, try multi-query retriever, fix chunking
Context PrecisionNoisy irrelevant chunksMMR retriever, metadata filtering, tighter similarity threshold
Answer RelevanceAnswer drifts off-topicClearer prompt, few-shot examples, add explicit task instruction
💡 Simple: Faithfulness measures whether the answer is grounded in retrieved documents (no hallucination — 1.0 = fully grounded). Answer relevance measures whether the response actually addresses the question. Both use an LLM as judge. Run these in CI so quality regressions are caught before they reach production.

Edge Cases & Failure Modes
What can silently break your RAG pipeline
HIGH
👻
Faithfulness Hallucination
LLM answers beyond the retrieved context or uses training knowledge to fill gaps. Appears confident but is fabricated.
Strict system prompt: "Answer ONLY from the provided context. If the answer is not in the context, say 'I don't know'."
HIGH
✂️
Chunk Boundary Split
Key sentence split across two chunks. Retrieving chunk A gives incomplete info. Chunk B alone also lacks context.
Use chunkOverlap (200+ chars). Parent-document retriever: index small chunks but return full parent doc.
HIGH
🔢
Embedding Mismatch (Index vs Query)
Indexed with model A (e.g., ada-002). Queried with model B (e.g., text-embedding-3-small). Vectors are incompatible — completely wrong results.
Record embedding model name in metadata. Enforce same model for index and query. Re-index if model changes.
MED
📊
Table / Structured Data Loss
PDF tables converted to flat text lose row/column relationships. Semantic search on "revenue Q3" may retrieve the right page but wrong cell.
Use tabular extractors (tabula-js). Store table as markdown with column headers. Tag metadata: {type: "table"}.
MED
🌊
Context Window Overflow
Retrieved k=10 chunks × 1000 chars = 10,000 chars. Plus prompt, history, and system message → exceed model context limit → truncation or error.
Reduce k, reduce chunkSize. Use LongContextReorder: put most relevant chunks first (recency bias in LLMs).
MED
🔄
Stale Index
Documents updated but vector store not re-indexed. LLM answers based on outdated chunks. Especially harmful in policy/price docs.
Store doc hash + last_updated in metadata. On doc update, delete old vectors by doc_id and re-embed. Schedule incremental re-indexing.
LOW
🈳
Language Mismatch
Docs in English, query in French. Embedding models are multilingual (e5-multilingual) but may still underperform vs same-language retrieval.
Translate query to doc language before embedding, or use dedicated multilingual embeddings (multilingual-e5-large).
LOW
🧩
Lost-in-the-Middle
LLMs perform better on information near the start or end of the context. Middle chunks are effectively ignored even if highly relevant.
Use LongContextReorder to place most relevant chunks at start and end. Reduce k to minimise middle context.
💡 Simple: The most common RAG failure is not bad retrieval — it is relevant documents getting retrieved but the LLM ignoring them (lost-in-the-middle effect). Always put the most relevant chunks first and last in the prompt. Metadata filtering (date range, document type) is often more important than vector similarity for precision tasks like legal or financial Q&A.
