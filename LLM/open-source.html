Transformers.js — AutoTokenizer + AutoModel (Node.js)JS
// npm install @xenova/transformers
import { AutoTokenizer, AutoModelForCausalLM } from "@xenova/transformers";

const modelId   = "Xenova/Qwen1.5-0.5B-Chat";  // ONNX-converted Hub model
const tokenizer = await AutoTokenizer.from_pretrained(modelId);
const model     = await AutoModelForCausalLM.from_pretrained(modelId);

// Apply chat template — adds model-specific special tokens
const messages  = [
  { role: "system", content: "You are a helpful assistant." },
  { role: "user",   content: "What is LoRA?" },
];
const { input_ids } = tokenizer.apply_chat_template(messages, {
  tokenize:          true,
  return_dict:       true,
  add_generation_prompt: true,
});

const outputs = await model.generate(input_ids, {
  max_new_tokens: 200,
  do_sample:      true,
  temperature:    0.7,
  top_p:          0.9,
});

// Decode only newly generated tokens
const newTokens = outputs.slice(null, [input_ids.dims[1], null]);
console.log(tokenizer.decode(newTokens[0], { skip_special_tokens: true }));

Instruction Fine-Tuning & Data Preparation
SFT · JSONL format · Chat template · Dataset curation

Supervised Fine-Tuning (SFT) teaches a base model to follow instructions by training on (instruction, response) pairs. The model learns to map instructions to desired outputs.

Training data format — JSONL (one JSON object per line):

  {"messages": [{"role":"system","content":"You are a customer support agent."},
                {"role":"user","content":"How do I reset my password?"},
                {"role":"assistant","content":"Go to Settings → Security → Reset Password..."}]}

  {"messages": [{"role":"user","content":"Translate to French: Hello"},
                {"role":"assistant","content":"Bonjour"}]}

After tokenization + chat template:
  <|system|>You are a customer support agent.<|end|>
  <|user|>How do I reset my password?<|end|>
  <|assistant|>Go to Settings → Security...<|end|>

Training loss computed ONLY on assistant tokens — not system/user tokens.
Loss mask ensures model learns to generate responses, not repeat prompts.

How to fine-tune as a JS developer: SFT training requires Python + GPU (TRL / PEFT libraries are Python-only). Your JS workflow is: prepare data → trigger training → consume the model.

Prepare JSONL dataset & upload to HF Hub (JS)JS
// npm install @huggingface/hub
import { uploadFile } from "@huggingface/hub";

// Build your JSONL dataset in memory
const rows = [
  { messages: [
    { role: "system",    content: "You are a customer support agent." },
    { role: "user",      content: "How do I reset my password?" },
    { role: "assistant", content: "Go to Settings → Security → Reset Password…" },
  ]},
  // … more examples
];
const jsonl = rows.map(r => JSON.stringify(r)).join("\n");

// Upload to HuggingFace Hub dataset repo
await uploadFile({
  repo: { type: "dataset", name: "my-org/support-dataset" },
  file: { path: "train.jsonl", content: new Blob([jsonl]) },
  credentials: { accessToken: process.env.HF_TOKEN },
});
Trigger SFT via HuggingFace AutoTrain API (JS)JS
// HuggingFace AutoTrain — no Python or GPU needed on your end

  model:    "my-org/my-sft-job",
  messages: [{ role: "user", content: "How do I reset my password?" }],

The HuggingFace AutoTrain API lets you trigger a fine-tuning job from JavaScript without writing any Python training code yourself.

LoRA & QLoRA — Parameter-Efficient Fine-Tuning
Freeze the base model; train only low-rank adapter matrices

LoRA (Low-Rank Adaptation) freezes all original model weights and injects small trainable matrices into attention layers. QLoRA extends this by loading the base model in 4-bit quantization — enabling 70B+ model fine-tuning on a single consumer GPU.

LoRA Math:

  Original weight:  W  (e.g., 4096×4096 = 16.7M params)  ← FROZEN
  LoRA adapters:    A (4096×r) and B (r×4096)             ← TRAINABLE
                    where r = rank (typically 8–64)

  Forward pass:  output = (W + A×B) × input
  Training:      only A and B are updated via backprop

  Parameter reduction:
    Full fine-tune: 16.7M params for one weight matrix
    LoRA r=16:      4096×16 + 16×4096 = 131K params  ← 128× fewer!

QLoRA = LoRA + 4-bit quantized base model:
  Base model loaded in NF4 (Normal Float 4-bit)  → ~4× less VRAM
  LoRA adapters remain in bfloat16               → high-precision gradients
  Double quantization: quantize the quantization constants too → further savings

  Llama-3 8B full fine-tune:  ~120 GB VRAM (8× A100)
  Llama-3 8B QLoRA:           ~10 GB VRAM (single RTX 3090!)

LoRA/QLoRA training is Python-only (PEFT + bitsandbytes require PyTorch). As a JS developer you: use AutoTrain to run LoRA (shown in Block 3), then consume the merged model via the HF Inference API or Ollama.

Using a LoRA-fine-tuned model from JSJS
// After training completes, the adapter is merged and pushed to Hub
// The merged model behaves like any normal Hub model

// Option A — HF Inference API (cloud, no GPU needed)
import { HfInference } from "@huggingface/inference";
const hf = new HfInference(process.env.HF_TOKEN);

const result = await hf.chatCompletion({
  model:    "my-org/llama-3-lora-merged",   // your merged LoRA model on Hub
  messages: [{ role: "user", content: "Help me with a support ticket." }],
  max_tokens: 300,
});

// Option B — Transformers.js (local, small models only)
// Convert merged model to ONNX first:
//   pip install optimum  →  optimum-cli export onnx --model my-org/lora-merged ./onnx-model
import { pipeline } from "@xenova/transformers";
const gen = await pipeline("text-generation", "my-org/llama-3-lora-merged");

// Option C — Ollama (local GGUF, any size)
// Convert to GGUF:
//   pip install llama.cpp  →  python convert_hf_to_gguf.py ./merged-model
// Then: ollama create my-model -f Modelfile  →  ollama run my-model
import OpenAI from "openai";
const ollama = new OpenAI({ baseURL: "http://localhost:11434/v1", apiKey: "ollama" });
const chat   = await ollama.chat.completions.create({
  model:    "my-model",
  messages: [{ role: "user", content: "Help me with a support ticket." }],
});
💡 Simple: Instead of retraining all 7 billion parameters, LoRA adds tiny adapter matrices (A × B) that are 128× smaller than the original weight matrices. QLoRA freezes the base model in 4-bit to save VRAM and trains only the adapters in fp16. Result: fine-tune a 7B model on a single 16GB consumer GPU in 30–60 minutes at near-identical quality.

Quantization
INT8 · INT4 · GPTQ · GGUF · AWQ — run large models on small hardware

Quantization reduces model weight precision from 16-bit float to 8-bit or 4-bit integers. This cuts VRAM and RAM by 2–4×, increases throughput, and enables edge/consumer deployment — at a small quality cost.

Precision comparison:

  float32  (FP32):  4 bytes/param  →  7B model = 28 GB  (training baseline)
  bfloat16 (BF16):  2 bytes/param  →  7B model = 14 GB  (standard inference)
  int8     (INT8):  1 byte/param   →  7B model =  7 GB  (minimal quality loss)
  int4     (INT4):  0.5 bytes/param →  7B model =  3.5 GB (noticeable but acceptable)

Quality degradation (typical):
  BF16 → INT8:  perplexity +0.1–0.5%   (barely noticeable)
  BF16 → INT4:  perplexity +2–5%       (acceptable for most tasks)
  BF16 → INT2:  perplexity +15–30%     (significant degradation)

Post-Training Quantization (PTQ) formats:
  GPTQ    — weight-only INT4, GPU-optimised, calibrated on small dataset
  GGUF    — llama.cpp format, CPU-friendly, mixed precision layers, used by Ollama
  AWQ     — Activation-aware, smarter than GPTQ, preserves important channels
  INT8 (bitsandbytes) — dynamic activation quantization at inference time

Model Alignment — RLHF, DPO & SFT
From capable but unsafe to helpful, harmless, and honest

A base model (pre-trained on raw text) can complete text but doesn't follow instructions safely. Alignment transforms it into a helpful assistant that refuses harmful requests and gives useful responses.

Alignment Pipeline:

  ┌──────────────────┐    SFT     ┌─────────────────────┐
  │   Base Model     │───────────▶│   SFT Model         │
  │  (pre-trained)   │            │  follows instructions│
  └──────────────────┘            └──────────┬──────────┘
                                              │
                                    RLHF or DPO
                                              │
                                              ▼
                                  ┌─────────────────────┐
                                  │   Aligned Model      │
                                  │  helpful + harmless  │
                                  └─────────────────────┘

RLHF (Reinforcement Learning from Human Feedback):
  1. Collect human preference data: {prompt, response_A, response_B, preferred: A}
  2. Train a Reward Model (RM) to predict human preferences
  3. Use PPO (Proximal Policy Optimization) to fine-tune the SFT model
     to maximise RM score while staying close to SFT baseline (KL penalty)
  → Complex, unstable training. Requires large preference datasets.

DPO (Direct Preference Optimisation):
  1. Same preference data: {prompt, chosen_response, rejected_response}
  2. ONE fine-tuning step — no separate reward model needed
  3. Loss: increase log-prob of chosen, decrease log-prob of rejected
  → Simpler, more stable. GPT-4 class models often use DPO variants.

RLAIF (RL from AI Feedback):
  Replace human annotators with a strong LLM (e.g., Claude) to generate
  preference labels at scale. Used in Constitutional AI (Anthropic).

DPO/RLHF training is Python-only (TRL + PyTorch). As a JS developer you prepare preference data, trigger training via AutoTrain, then consume the aligned model.

Build preference dataset & trigger DPO via AutoTrain (JS)JS
// Preference dataset format: {prompt, chosen, rejected}
const preferences = [
  {
    prompt:   "How do I fix a bug?",
    chosen:   "First, identify the root cause by reading error logs. Then add a test that reproduces the bug before fixing it.",
    rejected: "Just try different things until it works.",
  },
  // … more examples
];

// Upload to Hub (same uploadFile pattern as Block 3)
const jsonl = preferences.map(r => JSON.stringify(r)).join("\n");

// Trigger DPO training via AutoTrain API
await fetch("https://huggingface.co/api/autotrain/create", {
  method:  "POST",
  headers: { "Authorization": `Bearer ${process.env.HF_TOKEN}`, "Content-Type": "application/json" },
  body: JSON.stringify({
    project_name: "my-dpo-job",
    task:         "llm-dpo",
    base_model:   "my-org/my-sft-model",   // start from SFT model
    dataset:      "my-org/preference-data",
    params: { beta: 0.1, learning_rate: 5e-7, num_train_epochs: 1 },
  }),
});

// ── Use the aligned model from JS ────────────────────────────────────
// DPO-aligned models on the Hub behave like any other model — just call them normally
import { HfInference } from "@huggingface/inference";
const hf     = new HfInference(process.env.HF_TOKEN);
const answer = await hf.chatCompletion({
  model:    "my-org/my-dpo-job",
  messages: [{ role: "user", content: "How do I fix a bug?" }],
});
// Returns the "chosen"-style response — more thoughtful and structured

// DPO loss (conceptual reference):
// L = -E[ log σ( β × [ (logπ(chosen|x) - logπ_ref(chosen|x))
//                     - (logπ(rejected|x) - logπ_ref(rejected|x)) ] ) ]
// The model learns to increase P(chosen) and decrease P(rejected)
// relative to the SFT reference baseline (controlled by β)

                    │                                │

                        YES                    NO

Fine-tune when:                         RAG when:
  ✓ Style/format must be exact           ✓ Knowledge needs to be current
  ✓ Domain has custom vocabulary         ✓ Sources must be citable
  ✓ Latency-critical (no retrieval step) ✓ Low-to-zero training budget

💡 Simple: Three tools for different problems: prompting is free and instant but limited by context size; RAG adds external knowledge without any training; fine-tuning permanently changes the model's behaviour. Start with prompting, add RAG when you need current or private knowledge, and reach for fine-tuning only when RAG + prompting hit a quality ceiling.

Edge Cases & Failure Modes
The traps that break fine-tuning experiments
HIGH
💀
Catastrophic Forgetting
SFT on a narrow domain makes the model forget general capabilities. Ask it to write Python after fine-tuning on medical text — quality collapses.
Use LoRA (base weights frozen). Mix general instruction data with domain data (5–10% general). Evaluate on general benchmarks after each epoch.
HIGH
🎭
Reward Hacking (RLHF)
Model learns to maximise reward model score, not actual quality. Produces verbose, sycophantic responses. Reward model exploited by adversarial outputs.
KL penalty (beta) to keep policy near SFT baseline. Periodically retrain reward model on new data. Use DPO instead — inherently more stable.
HIGH
📊
Training Data Quality
A fine-tuned model is only as good as its training data. Noisy labels, inconsistent formatting, or bad responses in SFT data directly harm quality.
Deduplicate, filter length outliers, manually review 100+ samples. Use LLM judge to score training response quality before including.
MED
📉
Quantization Quality Cliff
4-bit quantization works well for most tasks but collapses on long-form reasoning, math, or structured output where precision matters most.
Benchmark before deploying. Prefer AWQ models over GPTQ at the same bit depth — better quality. For Ollama use ollama pull model:q8_0 to pull INT8 instead of the default Q4.
MED
⚙️
LoRA Rank Too Low
r=4 can't capture complex style changes. Fine-tuned model reverts to base behaviour on held-out examples — under-fitting.
Start with r=16. Scale to r=64 if quality is insufficient. Monitor training loss — it should decrease smoothly, not plateau immediately.
MED
💬
Chat Template Mismatch
Training used Llama-3 template (<|eot_id|>) but inference uses wrong template or none. Model produces garbled output or doesn't stop generating.
In Transformers.js use tokenizer.apply_chat_template(). For Ollama/HF Inference API, pass messages in the standard roles format — the server applies the template automatically.
LOW
📦
VRAM OOM During Training
Gradient accumulation doesn't free memory. Batch size 1 with long sequences still OOM. Mixed precision saves VRAM but doubles gradient compute.
When using AutoTrain, set gradient_checkpointing: true, reduce max_seq_length, or pick a smaller base model. For Transformers.js use dtype: "q4" quantization to cut memory usage.
LOW

License Violations
Many "open" models have non-commercial licences (LLaMA 3 commercial use requires Meta approval above 700M MAU). Fine-tuned derivatives inherit restrictions.
Check Hub model card before using commercially. Prefer Apache 2.0 (Qwen 2.5, Mistral 7B) or MIT licensed models for unrestricted use.
💡 Simple: Common open-source pitfalls: licence confusion (Llama 3 has usage restrictions — use Qwen 2.5 or Mistral for unrestricted commercial use), tokenizer mismatch (always load the tokenizer shipped with the exact model checkpoint), and VRAM overestimation (4-bit quantised 7B needs ~6GB, not 14GB — people consistently over-provision hardware).
