Module 2 — Architecture

Transformer Architecture, Tokenization & Model Types

The full internal journey: raw text → tokens → embeddings → attention layers → logits → next token. Covers encoder-only, decoder-only, and encoder-decoder models.

0
End-to-End: Text In → Token Out
How raw text flows through a Transformer from input to prediction
Raw Text: "Hello world"
      │
      ▼ [Tokenizer]
Token IDs:  [9906, 1917]    ← integer IDs from a vocabulary of ~50,000–128,000 tokens
      │
      ▼ [Token Embedding Table]
Vectors:  [[0.12,-0.44,...], [0.87,0.23,...]]   ← shape: (seq_len, d_model)
      │
      ▼ [Positional Encoding / Learned Positional Embedding]
Vectors with position info:  shape still (seq_len, d_model)
      │
      ▼ [Transformer Block × N]
  ┌─────────────────────────────────────────────────────┐
  │  LayerNorm                                          │
  │  Multi-Head Self-Attention  → attend to all tokens  │
  │  Residual connection (+)                            │
  │  LayerNorm                                          │
  │  Feed-Forward Network (MLP)                         │
  │  Residual connection (+)                            │
  └─────────────────────────────────────────────────────┘
      │
      ▼ [Final LayerNorm]
      │
      ▼ [Linear projection → vocabulary size]
Logits:  shape (seq_len, vocab_size)  — one score per token per position
      │
      ▼ [Softmax → sample]
Next token ID  →  decode back to text
💡 Simple: Text enters as words, gets chopped into token IDs, then each ID is mapped to a static float vector via a lookup table — no relationships yet. Position info is added on top. Only then do the Transformer attention blocks run — that's the first point where tokens "see" each other and cross-token relationships are established. Finally the last vector is projected back to a predicted word. The entire journey takes ~20ms on a modern GPU.
★
Two Different Pipelines: General LLM vs RAG
Same building blocks — different execution paths and different embedding roles

⚡ General LLM (single model)

User text
  ↓ Tokenizer
Token IDs  [42, 1234, 567, ...]
  ↓ Static token embedding lookup     ← Layer 0
Token vectors  (context-free, 1 per token)
  ↓ + Positional encoding
Position-aware vectors
  ↓ Transformer blocks × N            ← TA starts HERE
    (causal self-attention + FFN)
Contextual vectors
  ↓ Linear → vocab_size
Logits → Softmax → Next token → text

One model. Causal (left-to-right) attention. The embedding step is just a table lookup — no Transformer computation there.

🔍 RAG (two models, two TA passes)

── INDEXING (offline) ─────────────────────
Documents → chunk into text pieces
  ↓ Embedding model (encoder Transformer)
    Tokenize → static lookup
    + positional encoding
    → Bidirectional attention × N  ← TA #1
    → Pool all token vectors
Chunk vectors [768/1536-dim] → Vector DB

── QUERYING (per request) ─────────────────
User query
  ↓ Same embedding model             ← TA #1 again
Query vector
  ↓ Cosine search → Top-K chunks
Retrieved text chunks
  ↓ Build: [System + Chunks + Query]
  ↓ LLM tokenize → static lookup
    + positional encoding
    → Causal attention × N           ← TA #2
    → Next token
Response text

Two models. Transformer runs twice — inside the encoder (bidirectional) and inside the LLM (causal). Embedding model must be the same for indexing and querying.

PropertyGeneral LLM flowRAG flow
Number of models1 (decoder-only LLM)2 — encoder embedding model + decoder LLM
Transformer runsOnce (inside LLM)Twice — encoder for embeddings + LLM for generation
Attention typeCausal (left-to-right only)Bidirectional (encoder) + Causal (decoder)
Embedding usedStatic token lookup — context-freeContextual chunk vectors — context-aware
External storageNoneVector DB (Pinecone, Chroma, pgvector…)
Knowledge sourceModel weights onlyModel weights + retrieved documents
Updatable without retraining?❌ No✅ Yes — update the vector DB
Offline phase?❌ No — just inference✅ Yes — indexing pipeline runs first
💡 Simple: A general LLM call is one model, one Transformer pass, token-by-token generation. RAG is two models and two Transformer passes — an encoder Transformer first converts chunks and queries into comparable vectors (bidirectional, context-aware), then a decoder Transformer generates the answer using retrieved text as context. The "embedding" step means something different in each: static lookup inside the LLM, full encoder forward pass in RAG.
1
Tokenization
Converting raw text into integers the model can process

Tokenization splits text into tokens (sub-word units) and maps each to an integer ID. The model never sees raw characters — only token IDs.

AlgorithmHow it worksUsed in
BPE (Byte-Pair Encoding)Start with characters. Iteratively merge the most frequent adjacent pair. Compact frequent sub-words, rare words split into pieces.GPT-2, GPT-3, GPT-4, Llama
WordPieceSimilar to BPE but merge is based on likelihood increase, not frequency. Adds ## prefix for continuation tokens.BERT, RoBERTa, DistilBERT
SentencePieceLanguage-agnostic. Treats input as raw byte stream. No pre-tokenisation needed — handles any language/script.T5, ALBERT, XLNet, mT5
tiktokenOpenAI's fast BPE implementation. Uses byte-level BPE.GPT-3.5, GPT-4, Claude
Tokenization in JavaScript JS
// npm install @dqbd/tiktoken
import { encoding_for_model } from "@dqbd/tiktoken";

const enc  = encoding_for_model("gpt-4");
const text = "Tokenization splits text into sub-word units.";

const tokens = enc.encode(text);
// Uint32Array [6295, 1065, 2728, 5859, 1139, 1207, 12, 1178, 8316, 13]

// Decode back
const decoded = new TextDecoder().decode(enc.decode(tokens));
// "Tokenization splits text into sub-word units."

// Count tokens (important for API cost/limits)
const tokenCount = enc.encode(text).length;  // 10 tokens
enc.free();  // release WASM memory

// Transformers.js tokenizer (npm install @xenova/transformers)
import { AutoTokenizer } from "@xenova/transformers";
const tokenizer = await AutoTokenizer.from_pretrained("Xenova/llama-tokenizer");
const { input_ids } = await tokenizer("Hello world");
// Tensor { data: BigInt64Array [1n, 22172n, 1044n], dims: [1, 3] }

Token economy rules of thumb: ~1 token ≈ 4 English characters ≈ 0.75 words. A full page of text ≈ 500 tokens. Code is denser — fewer tokens per character.

💡 Simple: LLMs don't read characters or whole words — they read sub-word chunks. "ChatGPT" becomes 2–3 tokens. This matters because API costs, context limits, and response time all scale with token count, not character count. Always count tokens before API calls — never estimate by string length.
2
Embeddings
Turning token IDs into continuous vector representations

An embedding is a dense vector (array of floats) that represents a token. Semantically similar tokens end up close in this high-dimensional space.

Token Embedding Table:  shape = (vocab_size, d_model)
  e.g., vocab=50,257 tokens × d_model=768 floats = 38M parameters

  "king"   → [0.12, -0.44, 0.87, 0.23, ...]   d_model floats
  "queen"  → [0.11, -0.41, 0.89, 0.25, ...]   similar vector
  "Paris"  → [0.55,  0.70, 0.10, 0.90, ...]   different region

Positional Encoding (added on top of token embeddings):
  Option 1: Sinusoidal (original Transformer) — fixed, formula-based
  Option 2: Learned positions (GPT-2) — trainable lookup table
  Option 3: Rotary (RoPE, used by Llama, Mistral) — rotates Q and K vectors
             advantage: better length extrapolation beyond training context

Why positional encoding is critical: Self-attention is permutation-invariant — without position info, the model can't tell word order. Position encoding injects this information.

⚠️ Two very different things called "embeddings" — don't confuse them:
  • Static token embedding lookup (the first layer of every LLM) — a plain weight matrix. Token ID 4823 → row 4823 of the matrix. No Transformer computation, no attention, no awareness of other tokens. Vectors are context-free at this point — "bank" gets the same vector whether the sentence is about rivers or finance.
  • Contextual embeddings from encoder models (BERT, sentence-transformers, text-embedding-ada-002) — produced by running a full Transformer encoder over the input. Encoder models ARE Transformer Architecture. These vectors encode cross-token relationships. Used in RAG pipelines and semantic search.

After the static lookup + positional encoding, each token's vector still has zero knowledge of other tokens in the sequence. That changes only inside the self-attention layers.

Inspecting embeddings (Transformers.js) JS
// npm install @xenova/transformers
import { AutoModel, AutoTokenizer } from "@xenova/transformers";

const tokenizer = await AutoTokenizer.from_pretrained("Xenova/bert-base-uncased");
const model     = await AutoModel.from_pretrained("Xenova/bert-base-uncased");

// Get contextual embedding for "king"
const inputs    = await tokenizer("king");
const output    = await model(inputs);
const embedding = output.last_hidden_state.data;
// Float32Array of length 768 — 768-dimensional vector

// Cosine similarity helper
const cosine = (a, b) => {
  const dot  = a.reduce((s, v, i) => s + v * b[i], 0);
  const magA = Math.sqrt(a.reduce((s, v) => s + v * v, 0));
  const magB = Math.sqrt(b.reduce((s, v) => s + v * v, 0));
  return dot / (magA * magB);
};

const queenInputs = await tokenizer("queen");
const queenOut    = await model(queenInputs);
const similarity  = cosine(
  Array.from(embedding),
  Array.from(queenOut.last_hidden_state.data)
);
// typically 0.6–0.8 for semantically related words
💡 Simple: There are two kinds of embeddings. Inside an LLM the embedding lookup is just a table — token ID → fixed vector, no Transformer computation, no cross-token awareness. When you use BERT or a sentence-transformer to embed text for RAG, that's different: BERT runs a full Transformer encoder so "bank" in "river bank" gets a different vector than "bank" in "bank account". The static lookup inside an LLM can't do that — relationships only emerge once the attention blocks run.
3
Self-Attention Mechanism
The core innovation of the Transformer — how tokens attend to each other

Self-attention lets every token look at every other token and decide how much to "attend" to it when computing its own representation. This captures relationships across arbitrary distances in a single pass.

📌 Where the Transformer actually starts computing: The input to the very first attention block is token_embedding + positional_encoding — combined and position-aware, but still context-free. Self-attention is the first operation that lets tokens see each other.
"bank" (river bank) → same input vector as "bank" (bank account) ← before attention
After attention layer 1 → vectors begin to diverge (surrounding context absorbed)
After N layers       → "bank" fully disambiguated by its context 
For each token position:

Input vector x  →  multiplied by three weight matrices
  Q = x × W_Q   (Query:  "what am I looking for?")
  K = x × W_K   (Key:    "what do I have to offer?")
  V = x × W_V   (Value:  "what will I contribute?")

Attention score between position i and j:
  score(i,j) = Q_i · K_j  /  √d_k      ← dot product, scaled by √dimension

Attention weights (softmax normalises to sum to 1):
  α(i,j) = softmax(score(i,j))         ← how much does token i attend to token j?

Output at position i:
  out_i = Σ_j  α(i,j) × V_j            ← weighted sum of all Value vectors

Causal mask (for decoder/GPT-style):
  Future positions are masked to -∞ before softmax
  → token at position 3 cannot attend to positions 4, 5, 6...
    
Example: "The cat sat on the mat"
         Attention from "sat" to other tokens:

  "sat"  attends strongly to:  "cat" (subject), "mat" (location)
  "sat"  attends weakly to:    "The", "on"

  This is learned — not hard-coded — during training.

Multi-Head Attention: run self-attention H times in parallel with different weight matrices (heads). Each head can specialise in different relationship types (syntax, semantics, coreference, etc.). Concatenate all heads and project.

Scaled Dot-Product Attention — from scratch JS
// Pure JS — no framework needed. Q, K, V are 2D arrays (seq_len × d_k)
const softmax = (arr) => {
  const max  = Math.max(...arr);
  const exps = arr.map(x => Math.exp(x - max));
  const sum  = exps.reduce((a, b) => a + b, 0);
  return exps.map(e => e / sum);
};

// Matrix multiply: (n×m) × (m×p) → (n×p)
const matMul = (A, B) =>
  A.map(row =>
    B[0].map((_, j) => row.reduce((s, v, k) => s + v * B[k][j], 0))
  );

const transpose = (M) => M[0].map((_, j) => M.map(row => row[j]));

const scaledDotProductAttention = (Q, K, V, mask = null) => {
  const dK     = Q[0].length;
  const scale  = Math.sqrt(dK);
  // scores = Q @ Kᵀ / √dK
  const scores = matMul(Q, transpose(K)).map(row =>
    row.map(s => s / scale)
  );
  // Apply causal mask: set future positions to -Infinity
  if (mask) scores.forEach((row, i) =>
    row.forEach((_, j) => { if (mask[i][j] === 0) scores[i][j] = -Infinity; })
  );
  const weights = scores.map(row => softmax(row));
  return { output: matMul(weights, V), weights };
};

Computational complexity: O(n² · d) where n = sequence length. This is why very long contexts are expensive — doubling length quadruples attention cost.

💡 Simple: This is the first point in the pipeline where tokens actually interact. Before self-attention, every token's vector is isolated — "bank" looks identical whether the sentence is about rivers or finance. After the first attention layer, each token's vector has absorbed context from the others and they diverge. In "she threw the ball and it bounced", attention connects "it" back to "ball". All positions communicate in one parallel operation — no sequential loops.

Complete Transformer Architecture
All components assembled — one Transformer block
One Transformer Block (repeated N times — GPT-4: ~96 blocks)

  ← Embedding lookup + Positional encoding happen BEFORE block 1 (layer 0) →

                    Input x  (shape: seq_len × d_model)
                    = token_embedding + positional_encoding
                        │
                   LayerNorm 1
                        │
              ┌─────────┴──────────┐
              │   Multi-Head       │
              │   Self-Attention   │   H=12 to 96 heads
              └─────────┬──────────┘
                        │
              Residual:  x = x + attn_output   ← skip connection prevents gradient vanishing
                        │
                   LayerNorm 2
                        │
              ┌─────────┴──────────┐
              │  Feed-Forward      │
              │  Network (MLP)     │   FFN: Linear → GELU → Linear
              │  d_ff = 4 × d_model│   expands then contracts dimension
              └─────────┬──────────┘
                        │
              Residual:  x = x + ffn_output
                        │
                    Output x  (same shape: seq_len × d_model)

Model config examples:
  GPT-2 small:  d=768,  H=12, N=12,  params=117M
  GPT-3:        d=12288, H=96, N=96, params=175B
  Llama-3-8B:   d=4096,  H=32, N=32, params=8B  (GQA: 8 KV heads)

Grouped Query Attention (GQA): used in Llama 2/3, Mistral. Instead of H unique K,V heads, share K,V across groups. Reduces KV-cache memory at inference. Q still has H heads.

KV Cache: during autoregressive generation, K and V vectors for past tokens are cached. Without it, every new token would require recomputing attention over the entire history. Cache = O(n × layers × d_model) memory.

💡 Simple: The embedding lookup and positional encoding are "layer 0" — they happen before any Transformer block runs. Each block then does two things: attend to other tokens (share context across positions) and run a small MLP (apply non-linear processing). A residual connection preserves the original signal at each step to prevent gradient vanishing. Stack 32–96 of these blocks on top of the embedding layer and you have a full LLM.
5
Model Types: Encoder-only, Decoder-only, Encoder-Decoder
Three Transformer configurations — each suited to different tasks
ENCODER-ONLY (Bidirectional Attention)
  Input:  [CLS] The cat [MASK] on the mat [SEP]
          ← all tokens can see all other tokens (no causal mask) →
  Output:  contextual embedding for each token
  Use:    classification, NER, sentence similarity, question answering (extractive)
  Models: BERT, RoBERTa, DistilBERT, DeBERTa, ALBERT

DECODER-ONLY (Causal / Autoregressive)
  Input:  The cat sat on the
          ↓  ↓  ↓  ↓  ↓  ↓
          each token only sees past tokens (causal mask applied)
  Output: next token prediction
  Use:    text generation, chatbots, code generation, creative writing
  Models: GPT-2/3/4, Llama, Mistral, Falcon, Claude, Gemini, Command R

ENCODER-DECODER (Cross-Attention between enc. and dec.)
  Encoder: reads entire input (bidirectional)
       ↕  cross-attention
  Decoder: generates output autoregressively, attending to encoder output
  Use:    translation, summarisation, question generation
  Models: T5, BART, mT5, FLAN-T5, mBART
PropertyEncoder-onlyDecoder-onlyEncoder-Decoder
Attention typeBidirectional (full)Causal (left-to-right only)Bidirectional enc + Causal dec + Cross-attention
Best forUnderstanding tasksGeneration tasksSeq2seq: translation, summarisation
Chat / instruction following❌ (not generative)✅ (primary use)✅ (but less common now)
Embedding qualityExcellent (BERT embeddings)Good with poolingGood via encoder
Inference costSingle forward passN forward passes (one per token)Encoder once + N decoder passes
💡 Simple: Encoder-only (BERT) reads the whole sentence both ways — best for classifying and understanding. Decoder-only (GPT, Llama) reads left-to-right and predicts next tokens — best for chatbots and generation. Encoder-Decoder (T5) encodes input then generates output — best for translation. For building apps, you almost always want decoder-only.
⚠️ Edge Cases & Tricky Architecture Details
Things that trip up even experienced practitioners
HIGH
🔢
Context Length Limit
Attention is O(n²). Models have a fixed max context (GPT-4: 128K, Llama-3: 8K–128K). Exceeding it silently truncates or errors.
Count tokens before API call. Use chunking + RAG for long documents.
HIGH
🔤
Unknown / Rare Tokens
Rare words, names, foreign characters, and special symbols get split into many tokens. "Übersetzung" → 5+ tokens. Model sees fragments, not the full word.
Expand vocabulary via fine-tuning if your domain has many rare terms.
MED
📍
Position Extrapolation
Models trained on 4K context may degrade at 8K even if the architecture theoretically supports it. RoPE handles extrapolation better than absolute embeddings.
Use RoPE-based models (Llama, Mistral) or models specifically fine-tuned for long context.
MED
💾
KV Cache OOM
At inference, the KV cache grows linearly with sequence length. A 70B model serving 100K-token context needs ~70 GB just for the cache.
Use sliding window attention (Mistral), quantised KV cache, or paged attention (vLLM).
MED
📊
Token vs Character Counting
API limits and costs are in tokens, not characters. "Supercalifragilistic" = 7 tokens. Emoji = 2–4 tokens. Chinese characters = 1–2 tokens each but complex compound words more.
Always count tokens with tiktoken before sending. Never estimate by character count for billing.
LOW
🔀
Tokenizer Mismatch
Different models use different tokenizers. A BERT tokenizer applied to a GPT-4 model (or vice versa) produces wrong token IDs and broken results.
Always load the tokenizer that matches the model: AutoTokenizer.from_pretrained(modelId) in Transformers.js, or use the correct tiktoken encoding per model.
