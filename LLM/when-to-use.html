Module 10 — When to Use

When to Use What — Decision Reference

Concrete, scenario-driven guidance across every LLM decision: model selection, knowledge strategy, fine-tuning method, agent pattern, deployment target, and more.

1
Which Model to Use
Standard LLM · Reasoning model · SLM · Embedding model
Standard LLM
GPT-4o · Claude 3.5 · Gemini 1.5
Everyday chat, summarisation, extraction, translation, content generation, code assistance, customer support
Reasoning Model
o3 · o4-mini · DeepSeek-R1 · Claude 3.7
Complex math, multi-step code generation, scientific reasoning, formal proofs, tasks where single-pass LLMs consistently fail
Small LLM (SLM)
Phi-3.5-Mini · Qwen2.5-7B · Llama-3.2-1B
On-device / offline inference, privacy-sensitive data, high-volume low-cost tasks, well-defined focused domain (classify, extract, summarise)
Embedding Model
text-embedding-3-small · nomic-embed · BGE
Semantic search, RAG retrieval, sentence similarity, clustering, classification via cosine distance. NOT for text generation.
ScenarioBest choiceWhy
Summarise 50 support tickets per minuteSLM fine-tunedCheap, fast, private; quality matches GPT-4 on narrow task
Solve competitive math olympiad problemo3 (high effort)Needs test-time reasoning chain; standard LLM scores <15%
Chatbot that works offline on iPhoneLlama-3.2-1B (quantised)Only 1B params fits iPhone RAM; runs at 30 tok/s
Find similar documents in a knowledge baseEmbedding modelCosine similarity over embeddings, not generation

✅ Use Reasoning Models when
  • Task consistently fails with standard models
  • Multi-step chains where one bad step fails the whole answer
  • Math, proofs, algorithm correctness
  • Complex code: multi-file refactors, algorithmic design
  • Quality >> cost and latency is acceptable (10-120s)
❌ Skip Reasoning Models when
  • Simple Q&A, summarisation, extraction
  • Latency < 2s is required (real-time chat, typeahead)
  • High-volume workload — cost is 10-100× standard models
  • Task is well-defined and standard models already nail it
  • Streaming UX — thinking tokens add significant delay
💡 Simple: Default to a standard model for everyday tasks. Switch to a reasoning model only when the task genuinely requires multi-step thinking (math, hard code). Use SLMs when cost, latency, or privacy demand local execution. Use embedding models only for search/similarity — never for generating text.

Prompting vs RAG vs Fine-tuning
Choosing your knowledge injection strategy
Does the model already have the knowledge?
│
├── YES → Does the output format/style need to change?
│          ├── NO  → ✅ Just prompt it (zero-shot or few-shot)
│          └── YES → ✅ Few-shot prompting or light SFT fine-tuning
│
└── NO  → Is the missing knowledge in documents / a database?
           ├── YES → ✅ RAG (retrieve relevant chunks, pass as context)
           └── NO  → Is it a new skill/behaviour the model lacks entirely?
                      ├── YES (small data <10K examples)  → ✅ LoRA / QLoRA fine-tune
                      └── YES (large data, new domain)    → ✅ Full fine-tune or continued pre-train
TechniqueUse whenSkip whenCost
Zero-shot promptingModel knows it; clear instruction is enoughOutput format is critical; task is ambiguousFree
Few-shot promptingFormat-sensitive task; 2–5 examples in contextPrompt gets too long (expensive); examples change oftenExtra input tokens
RAGPrivate data, current events, large knowledge base, citable answersKnowledge fits in context; query is not information-seekingInfra + embedding API
LoRA / QLoRA fine-tuneDomain tone/style, structured output, specialised task, slow-changing knowledgeKnowledge changes frequently; you have no labelled dataGPU time, one-off
Full fine-tuneMaximum quality, new language/domain, multi-task specialisationYou have <1K examples or limited GPU budgetHigh (8×A100)
RAG + fine-tuneNeed domain tone AND current data (e.g. medical chatbot)Adds complexity — only when each alone is insufficientBoth costs
✅ Use RAG when
  • Answering questions about private / internal documents
  • Knowledge changes frequently (news, prices, inventory)
  • Users need cited, verifiable sources
  • Knowledge base is too large to fine-tune on
  • You want to add knowledge without any training cost
❌ Use Fine-tuning instead when
  • Model needs a new output style/format permanently
  • Task requires speed and context stuffing is too slow
  • Knowledge is stable (doesn't change month-to-month)
  • You have 1K+ high-quality labelled examples
  • Latency is critical and retrieval step is unacceptable
💡 Simple: Start with prompting — it costs nothing and works for most tasks. Add RAG when the model lacks current or private knowledge. Reach for fine-tuning only when you need permanent behaviour change (style, format, specialised skill) that prompting cannot reliably produce. Most apps need prompting + RAG; very few need fine-tuning.
📄 Building RAG over PDF documents? PDFs introduce specific challenges not covered in standard RAG — multi-column layouts, embedded tables, scanned images, and inconsistent formatting require dedicated pre-processing. Which RAG Retrieval Strategy
Basic cosine · Hybrid BM25 · MMR · Multi-query · Reranker · GraphRAG
Basic Vector Search
Cosine similarity top-k
Small corpus (<10K docs), clear well-formed queries, good baseline to start. Simple to implement, no extra infra.
Hybrid Search
BM25 + vector (RRF merge)
Queries contain exact product names, codes, or IDs. Mix of fuzzy semantic queries and exact-match keyword queries. +15-20% quality over pure vector.
MMR Retrieval
Maximal Marginal Relevance
Need diverse retrieved chunks (not 5 near-identical paragraphs). Long-form synthesis tasks. Document coverage over depth.
Multi-Query
LLM generates 3 sub-queries
Short or ambiguous user queries ("tell me about our policy"). Different phrasings retrieve different but relevant documents. Best for vague Q&A.
Cross-Encoder Reranker
Retrieve 50 → rerank → top 5
High-precision required (legal, medical, financial). Can afford +0.3-0.5s latency. Biggest quality jump for the least complexity. Always add to production RAG.
GraphRAG
Knowledge graph + vector
Multi-hop questions that span multiple documents ("What is the relationship between X and Y from these docs?"). Complex interconnected knowledge bases.
Your situationRecommended retrieval
MVP / prototype, need something working todayBasic cosine top-k
Queries include model numbers, product IDs, exact namesHybrid (BM25 + vector)
Users ask vague 1-5 word questionsMulti-query expansion
Top-k returns 5 paragraphs saying the same thingMMR retrieval
Going to production — quality matters mostHybrid + cross-encoder reranker
Questions require connecting facts across documentsGraphRAG or multi-hop retrieval
Need to filter by date, author, category before rankingMetadata pre-filter + vector search
Source documents are PDFs with tables, images, or scanned pagesMulti-modal pipeline → see Module 11 · PDF RAG
💡 Simple: For production, always combine at least two: hybrid search (vector + BM25) covers both semantic and exact-match cases, and a cross-encoder reranker ensures the most relevant chunk reaches the top. That combination alone gives 20-30% quality improvement over basic cosine search with minimal extra infrastructure.

✅ Use QLoRA when
  • GPU has ≤ 16 GB VRAM (RTX 4080/4090)
  • First fine-tuning attempt — low risk to experiment
  • Base model must stay usable (adapter is swappable)
  • Multiple fine-tuned variants needed (one base, many adapters)
  • Training data is 100–10,000 examples
❌ Use Full Fine-tuning instead when
  • Adapting an entirely new language or script
  • Training on 1M+ examples where adapter capacity is bottleneck
  • Need absolute maximum task performance
  • Doing instruction-tuning from scratch (base → instruct)
  • Multi-task training over many diverse objectives
✅ Use DPO when
  • Model follows instructions but tone/style is wrong
  • Need to reduce refusals or unsafe outputs
  • Have (prompt, good-response, bad-response) triples
  • Already have an SFT model as starting point
  • Want stability — DPO is far more stable than PPO
✅ Use GRPO instead when
  • Task has verifiable correct answers (math, code, logic)
  • Want to train reasoning ability (like DeepSeek-R1)
  • No human labellers — auto-verifier is enough
  • Want to avoid reward model training entirely
  • Scaling alignment to millions of examples cheaply
💡 Simple: 90% of fine-tuning projects should start with QLoRA — it runs on a consumer GPU, produces near full fine-tune quality, and is low-risk to experiment with. For alignment: use DPO if you have preference pairs and want safety/style tuning; use GRPO if your task has verifiable answers and you want to build reasoning capability.

Direct Call vs Chain vs Agent vs Multi-Agent
Choosing the right orchestration pattern
Direct API Call
Single-turn task, no tools needed, predictable output. Simplest and fastest. Use for summarisation, classification, Q&A with all context in prompt.
LCEL Chain
Fixed multi-step pipeline. Steps are always the same, in the same order. Use for RAG (retrieve → prompt → generate → parse), templated document generation.
ReAct Agent
Dynamic tool use — the model decides which tools to call. Number of steps is unknown at design time. Use for research assistants, search-based Q&A, data exploration.
LangGraph Agent
Complex state, loops, branching, human-in-the-loop approval. Need explicit control over agent flow. Use for multi-step workflows with conditional paths and checkpoints.
Multi-Agent
Task is too complex or long for one agent's context window. Benefits from parallel specialised sub-agents (researcher + coder + writer). A2A for cross-framework coordination.
ScenarioPatternReason
Summarise a documentDirect callSingle step, all context fits in prompt
Answer questions from a knowledge baseLCEL RAG chainFixed steps: retrieve → prompt → answer
Research assistant that searches and synthesisesReAct agentUnknown number of search steps needed
Code assistant that writes, runs tests, fixes bugsLangGraphLoop (write → test → fix) with conditional exit
Full software project: plan, code, review, deployMulti-agent supervisorParallel specialised agents; exceeds single context
Data pipeline: collect → clean → analyse → reportLangGraph with checkpointsLong pipeline, need to resume on failure
✅ Add agents when
  • Number of steps is unknown at design time
  • Task requires real-world tool use (search, code execution, API calls)
  • Human approval is needed before destructive actions
  • Task needs to resume across sessions (checkpointing)
  • Multiple specialised skills are required in one workflow
❌ Avoid agents when
  • A fixed chain already solves the task reliably
  • Latency is critical (agents add multiple LLM round-trips)
  • Task is high-stakes and unpredictable agent paths are risky
  • No tools are needed — direct call is always faster
  • You have no max_iterations guard — loops are dangerous without limits
💡 Simple: Use the simplest pattern that solves the problem. Direct calls for one-shot tasks. Chains for fixed pipelines. Agents only when the model genuinely needs to decide what to do next. Every step up in complexity adds latency, unpredictability, and debugging difficulty — only pay that cost when simpler patterns cannot handle the task.

TechniqueUse whenSkip whenGain
Quantization (INT4/INT8)VRAM is the bottleneck; consumer GPU; edge/mobile deploymentQuality is critical and accuracy loss matters; using API (handled by provider)4-8× memory reduction, 3-7% quality loss
Speculative DecodingLatency is critical; same-family draft+target; long outputsHigh-diversity outputs (draft acceptance drops); batched serving with mixed prompts2-3× faster generation

Batching (server-side)Throughput matters more than per-request latency; offline processingReal-time interactive use; latency SLA is tight2-10× throughput improvement
✅ Quantize to INT4 when
  • Running a 7B+ model on ≤ 16 GB VRAM
  • Deploying to mobile or browser (Transformers.js)
  • Task is language-level (chat, summarise) not precision math
  • Want to run larger models on available hardware
❌ Keep full precision when
  • Fine-tuning (quantization during training degrades gradients)
  • Scientific / numeric output where 3-7% error matters
  • Using API provider (quantization is their concern)
  • Embedding models (precision affects similarity scores)
💡 Simple: If you're self-hosting, always use FlashAttention (it's free) and quantize if VRAM is tight. Add semantic caching if many users ask similar questions — it's the single highest-ROI optimisation for production apps. Speculative decoding gives real latency wins but only when the draft and target models share training distribution.

Which Model Architecture
Decoder-only · Encoder-only · Encoder-Decoder · MoE · SSM · Hybrid
Decoder-only (GPT/Llama)
Text generation, chatbots, code generation, creative writing. Causal attention — reads left-to-right. The dominant architecture for everything generative.
Encoder-only (BERT)
Classification, NER, sentence similarity, semantic search embeddings. Bidirectional attention — sees full sentence. NOT for generating text.
Encoder-Decoder (T5/BART)
Translation, summarisation, question generation, text transformation. Encoder reads full input, decoder generates output. Seq-to-seq tasks.
MoE (Mixtral/DeepSeek)
Data-centre serving where quality-per-FLOP matters. Mixed domain tasks. Large cluster with GPU interconnect. Not suitable for consumer GPU deployment.
SSM / Mamba / RWKV
Very long sequences (>32K tokens) where transformer OOMs. Streaming data (audio, genomics, time-series). When throughput > precise long-range recall.
Hybrid (Jamba/Zamba)
Long context AND precise recall needed. Combines SSM (efficiency at scale) with attention layers (exact recall). Best of both at extra architectural complexity.
TaskArchitectureExample models
Chatbot, code assistant, creative writingDecoder-onlyGPT-4o, Llama-3, Mistral, Claude
Sentence similarity / embedding for RAGEncoder-onlyBERT, nomic-embed, BGE, E5
Summarisation, translationEncoder-Decoder or Decoder-onlyT5, BART, FLAN-T5, Claude (decoder)
High-quality serving with GPU clusterMoEMixtral 8×7B, DeepSeek-V3, GPT-4
100K+ token documents, streaming inferenceSSM or HybridMamba, RWKV, Jamba
On-device mobile inferenceTiny decoder-only (quantised)Phi-3.5-Mini, SmolLM2, Llama-3.2-1B
💡 Simple: For building apps today: use a decoder-only model (Llama, Mistral, GPT) for everything generative, and an encoder-only model (BERT, BGE) only if you need embeddings for semantic search. MoE, SSM, and hybrid architectures are mostly server-side concerns — you interact with them via API and the architecture is transparent to your code.

✅ Self-host when
  • Data privacy regulations (HIPAA, GDPR) prevent sending data to third parties
  • Volume is high enough that API cost > server cost (~10M+ tokens/day)
  • Need custom fine-tuned models not available via API
  • Latency SLA requires <100ms first token (no network round-trip)
  • You need full control over model version and behaviour
✅ Use managed API when
  • Building an MVP or prototype — ship in hours not weeks
  • Team lacks ML infrastructure expertise
  • Traffic is unpredictable — pay-per-use scales automatically
  • Need frontier models (GPT-4o, Claude 3.5) — not available to self-host
  • No compliance requirement preventing external API use
💡 Simple: Start with a managed API — zero infra, best models, ships in hours. Move to self-hosted (Ollama locally, vLLM in production) when data privacy mandates it or when API costs exceed hosting costs at your volume. Transformers.js is the right choice when the app must work offline or in the browser without any server.

Production Tooling & Protocols
LangSmith · MCP · A2A · Caching · Guardrails
LangSmith
Any production LLM app. Traces every call, evaluates quality, tracks costs. Add on Day 1 — you will need it when debugging goes wrong.
MCP Servers
When Claude or another MCP client needs to read/write external data (GitHub, databases, file systems) without custom integration code per tool.
A2A Protocol
When multiple agents from different teams, frameworks, or companies need to collaborate on tasks. Standardises inter-agent task delegation and result streaming.
Semantic Cache
FAQ bots, customer support, search — any app where many users ask similar questions. Cache by embedding similarity. 80-95% cache hit rates possible.
Input / Output Guards
Public-facing apps where users can inject malicious prompts. Classify inputs before sending to LLM. Validate structured outputs against schema. Always required for production.
Circuit Breaker
When primary model has availability or latency issues. Fall back to a cheaper/smaller model automatically. Prevents cascading failure across your app.
You need to…Tool / Pattern
Debug why the LLM gave a wrong answer last TuesdayLangSmith traces
Evaluate quality after a prompt or model changeLangSmith evaluations + dataset
Let Claude read your company's GitHub repos without custom codeMCP server (modelcontextprotocol/server-github)
Coordinate a research agent and a writing agent built by different teamsA2A protocol (Agent Cards + tasks/send)
Cut API costs when 70% of queries are similarSemantic cache (embed query, cache hit by similarity)
Stop users from injecting "ignore all previous instructions"Input classifier guard (detect injection before LLM call)
Ensure LLM always returns valid JSON schemaOutput validator (Zod) + retry on parse failure
Handle primary model outage without app downtimeCircuit breaker → fallback to GPT-4o-mini or local SLM
💡 Simple: Every production LLM app needs three things: LangSmith for observability (you cannot debug what you cannot see), input/output validation at system boundaries, and retry/fallback logic for API failures. Add MCP when your model needs external tools; add A2A when agents from different systems need to collaborate.

Which Prompt Engineering Technique
Zero-shot · Few-shot · CoT · ReAct · Self-consistency · ToT
TechniqueUse whenWhen to skip
Zero-shotSimple, clear task. Model has the knowledge. No special format needed.Output is consistently wrong or in wrong format.
Few-shot (2–5 examples)Format-sensitive output (JSON, tables, structured text). Domain-specific style. Classification with custom labels.Examples themselves are too long (wastes context). Examples change per request.
Chain-of-Thought (CoT)Multi-step math, logic puzzles, code debugging. Any task where one wrong step fails the answer. Add "think step by step".Simple factual recall — CoT adds noise. Latency-critical.
Self-consistencyAmbiguous reasoning. Generate N answers (temperature > 0), take majority vote. Improves reliability at cost of N× API calls.Deterministic tasks. Cost-sensitive. When temperature=0 is required.
ReAct (Reason + Act)Multi-step tasks that need tool use. Model alternates: thought → action → observation. Used in agents (see Block 5).No tools involved. Simple single-turn tasks.
Tree of Thought (ToT)Complex problems with multiple valid paths. Model explores, evaluates, and backtracks. Research tasks, strategy problems.Most production apps — overhead is high. Simpler CoT usually suffices.
Role prompting"You are a senior security engineer…" — improves domain-specific output quality and tone. Useful when domain expertise in response matters.Generic tasks where role adds no value. Can introduce unwanted persona bias.
Output format constraint"Respond ONLY as a JSON object with keys: name, age, city." — critical for any downstream parsing.When flexibility in response structure is acceptable.
✅ Always include
  • Delimiters around user input: use """ or XML tags to prevent prompt injection
  • Output format instruction when downstream parsing is needed
  • Negative constraint if there are known failure modes: "Do not include code", "Never make up citations"
  • Context boundary — tell the model explicitly what information it has and does not have
❌ Common prompt mistakes
  • Overloading system prompt with 5,000+ tokens of instructions — model ignores middle
  • Asking multiple unrelated tasks in one prompt — split into separate calls
  • Using vague verbs: "improve", "fix", "enhance" without criteria
  • Assuming the model remembers previous conversations — it does not
  • Not testing at temperature=0 first — add randomness only if needed
💡 Simple: Zero-shot first — it works surprisingly often. If format is critical, add 2–3 few-shot examples. If accuracy on multi-step problems is low, add "think step by step" (CoT). Everything beyond that (ToT, self-consistency) is for hard edge cases. The prompt engineering hierarchy: zero-shot → few-shot → CoT → agents → fine-tuning.
