Module 9 — Comparison

Old vs New — Architecture & Training Comparison

Side-by-side analysis of traditional LLM approaches versus cutting-edge techniques — when to use which, and what actually changed.

1
Dense Transformer vs Mixture of Experts (MoE)
Scaling parameters without scaling compute
Dense Transformer VS Mixture of Experts
Traditional Approach
Dense Transformer FFN
Every token passes through the same FFN weights on every layer. All parameters are active for every forward pass.
  • GPT-2 117M → all 117M params active per token
  • Llama-3 8B → all 8B params active per token
  • GPT-3 175B → all 175B params active per token
  • Doubling capacity = doubling compute cost
  • No specialisation — every expert does everything
Token → Embed → [Attn → FFN(W₁,W₂)] × L → LM-Head FFN: hidden = ReLU(xW₁ + b₁) · W₂ + b₂ W₁ ∈ R^{d_model × d_ffn} (ALL params active)
Modern Approach
Mixture of Experts (MoE)
Each token is routed to only k=2 of N expert FFNs. Most parameters are "dormant" — capacity scales cheaply.
  • Mixtral 8×7B → 56B params, only 13B active/token
  • DeepSeek-V3 → 671B params, only 37B active/token
  • GPT-4 (rumoured) → ~1.8T params, ~220B active
  • 4-8× parameters at 1.5-2× compute vs same-compute dense
  • Experts naturally specialise (code, math, language)
Token → Router → softmax(W_r · x) → top-2 experts ↓ weights [0.6, 0.4] Token → Expert₃(W₁³,W₂³) → output₃ × 0.6 Token → Expert₇(W₁⁷,W₂⁷) → output₇ × 0.4 ↓ weighted sum
MetricDense (7B)MoE (56B total / 13B active)
Total params7B56B
Active params/token7B (100%)13B (23%)
VRAM for inference~14 GB (fp16)~90 GB (all experts loaded)
Training cost1×~1.5-2× (due to load-balance loss)
Inference FLOPs/token~14 GFLOPs~26 GFLOPs (2 experts)
Quality at same computeBaseline+15-25% better
Use Dense When
  • Serving on consumer GPUs (<24GB VRAM)
  • Fine-tuning — MoE fine-tuning is harder
  • Latency is critical (fewer memory reads)
  • Deploying quantised models locally
Use MoE When
  • High-quality inference at data-center scale
  • Multi-GPU cluster with NVLink available
  • Mixture of domains (code + math + language)
  • Cost-per-quality ratio is the priority
Bottom line: MoE wins on quality-per-FLOP for large-scale serving. Dense wins for local deployment and fine-tuning workflows where VRAM loading all experts is prohibitive.
💡 Simple: Dense models use all parameters for every token — expensive to scale. MoE uses only 2 of 8 expert FFNs per token — 8× the parameters at only 2× the compute cost. The trade-off: you still load all experts into VRAM, so inference memory is much higher. Best for data-centre serving; not for consumer GPU deployment.

Quadratic Attention vs State Space Models (Mamba / RWKV)
Sequence length scalability
Transformer Attention O(n²) VS Mamba / RWKV O(n)
Traditional
Scaled Dot-Product Attention
Every token attends to every other token. Attention matrix is n×n — quadratic memory and compute with sequence length.
  • 1K tokens → 1M attention entries
  • 32K tokens → 1B attention entries (1 GB fp32)
  • 128K tokens → OOM on most consumer GPUs
  • Prefill latency scales as O(n²)
  • KV cache scales as O(n) per layer
Attention(Q,K,V) = softmax(QKᵀ / √d_k) · V Matrix QKᵀ ∈ R^{n×n} ← n² memory n=1K → 4MB (manageable) n=32K → 4GB (tight) n=128K→ 64GB (impossible w/o FlashAttn)
Modern
Mamba Selective SSM
Compresses sequence history into a fixed-size hidden state h. State update is O(1) per token — true linear complexity.
  • 128K tokens → same cost as 1K tokens per step
  • State size is constant regardless of sequence length
  • Selective: Δ, B, C depend on input (content-aware)
  • Inference: O(1) recurrent update per token
  • Training: O(n log n) via parallel scan
SSM: h_t = Ā h_{t-1} + B̄ x_t [O(d_state) memory] y_t = C h_t + D x_t Selective Mamba: Δ,B,C = f(x_t) — input-dependent Ā = exp(Δ A) Inference: constant state, O(1) per token step
MetricTransformer AttentionMamba SSM
Time complexity (prefill)O(n²·d)O(n·d_state)
Memory (KV/state)O(n·d) KV cacheO(d_state) fixed
Short-context qualityExcellentComparable
Long-context recallPerfect (full attention)Degrades (state compression)
Throughput at 128K ctxVery slow / OOMLinear — fast
Exact lookup tasksReliableCan miss (compressed)
Bottom line: SSMs are transformative for long-context streaming tasks (audio, genomics, real-time data). Transformers remain superior for tasks needing precise recall of arbitrary past tokens. Hybrid architectures (Jamba, Zamba) combine both: SSM layers for efficiency + attention layers for recall.
💡 Simple: Transformers remember everything perfectly but memory cost is quadratic — 32K tokens means a billion entries in the attention matrix. Mamba compresses all history into a constant-size state — memory never grows. Trade-off: SSMs may "forget" specific details from very long histories. Use transformers when you need precise long-range recall; use SSMs for streaming or long-context throughput.

Fixed Depth Transformer vs Mixture of Recursions (MoR)
Adaptive compute allocation per token
Fixed L layers per token VS Dynamic depth with weight sharing
Traditional
Fixed-Depth Transformer
Every token processes through exactly L layers regardless of token complexity. A space character gets the same compute as a complex reasoning step.
  • All tokens: 32 layers (e.g. Llama-3 8B)
  • "The" gets same FLOPs as "integrate(e^x²dx)"
  • Waste: simple tokens over-processed
  • Limitation: hard tokens under-processed
  • Scale = more layers for ALL tokens
Token₁ ("the") → L1 → L2 → ... → L32 → output Token₂ ("compute") → L1 → L2 → ... → L32 → output Token₃ (";") → L1 → L2 → ... → L32 → output Every token: same 32-layer path regardless of complexity
Modern
Mixture of Recursions (MoR)
One shared layer block (weights) is applied recursively. A router decides how many passes each token needs — simple tokens exit early.
  • Single shared block, applied 1–R times per token
  • Router: "Does this token need another pass?"
  • Simple tokens: 1-2 passes; complex: up to R passes
  • Total params: same as 1 layer, total compute: variable
  • Memory: weight sharing = tiny model footprint
SharedBlock (weights reused each recursion): Token₁ ("the") → [Block]¹ → exit (simple) Token₂ ("compute") → [Block]¹ → [Block]² → [Block]³ → exit Token₃ (";") → [Block]¹ → exit Router: sigmoid(W_r · h_t) → continue or exit? Depth per token: adaptive [1..R], avg ≈ R/2
MetricDense TransformerMoR (Mixture of Recursions)
Depth per tokenFixed L layersDynamic 1–R passes
Weight sharingNone (L × unique weights)Full (1 shared block)
Model size (params)L × d²1 × d² (tiny footprint)
FLOPs per tokenFixed (L × block)Variable (avg R/2 × block)
Hardware utilisationPredictableVariable (batching challenge)
Model availability (2025)UbiquitousResearch only
Bottom line: MoR is architecturally elegant — minimal parameters, adaptive compute. Still research-stage in 2025 with no production models. The key challenge is batching tokens with different depths on GPU. Watch for MoR × MoE hybrids combining expert routing with recursive depth.
💡 Simple: Standard transformers waste compute: a punctuation mark gets the same 32 layers of processing as a complex mathematical symbol. MoR lets simple tokens exit early and complex tokens recurse deeper — using the same shared weights. Elegantly efficient in theory, but still research-only in 2025 with no production models available.

Autoregressive Decoding vs Speculative Decoding
Inference speed without quality loss
1 token per forward pass VS Draft k tokens, verify in parallel
Traditional
Autoregressive Decoding
The target model generates one token per forward pass. Each pass is sequential — cannot be parallelised. Latency scales linearly with output length.
  • Target model (70B): 1 pass → 1 token
  • 100 tokens → 100 serial forward passes
  • GPU utilisation often low (memory-bandwidth bound)
  • Latency ∝ output_length × model_size
Prompt: "The capital of France is" T=1: model(prompt) → "Paris" T=2: model(prompt+"Paris") → " and" T=3: model(prompt+"Paris and") → " the" T=4: model(prompt+"Paris and the") → " most" ... 100 serial passes for 100 tokens
Modern
Speculative Decoding
Small fast "draft" model generates k tokens. Large target model verifies all k in a single batched pass — rejected tokens are corrected, accepted tokens are free.
  • Draft model (7B): generates k=5 tokens quickly
  • Target model (70B): verifies all 5 in 1 pass
  • If 4/5 accepted → 4 tokens in cost of ~1.2 passes
  • Typical speedup: 2-3× at same output quality
  • Zero quality loss — target model distribution preserved
Draft (7B, fast): "Paris" "and" "the" "Eiffel" "Tower" Target (70B, 1 pass): verify all 5 tokens in parallel Token 1 "Paris" → P_target ≥ P_draft → ACCEPT ✓ Token 2 "and" → P_target ≥ P_draft → ACCEPT ✓ Token 3 "the" → P_target ≥ P_draft → ACCEPT ✓ Token 4 "Eiffel" → P_target ≥ P_draft → ACCEPT ✓ Token 5 "Tower" → P_target < P_draft → REJECT, resample Result: 4 free tokens + 1 corrected = 5 tokens, cost ≈ 1.2 passes
MetricAutoregressiveSpeculative Decoding
Tokens per pass1k (typically 4-6)
Output qualityReferenceIdentical (provably)
Latency speedup1×2-3× (high acceptance)
Extra VRAM neededNoneDraft model overhead
Batch inferenceGoodComplex (variable accept rates)
Cold / OOD promptsNormal speedCan be slower (low acceptance)
Bottom line: Speculative decoding is a free lunch for latency-critical serving when draft and target model share the same domain/distribution. Gemini, Claude, and GPT deployments all use variants of this. Struggle: batched inference at scale, because different sequences have different acceptance rates.
💡 Simple: Normal decoding: 1 forward pass → 1 token. Speculative decoding: a small fast model drafts 5 tokens, the big model verifies all 5 in 1 pass. If 4 are accepted, you got 4 tokens for the cost of ~1.2 passes — mathematically identical quality at 2–3× the speed. The catch: only works well when the draft and target models share the same domain.

Single-Pass LLM vs Reasoning Models (Test-Time Compute)
Thinking before answering
Prompt → answer in one pass VS Prompt → think chain → answer
Traditional
Standard Instruction-Tuned LLM
Model maps prompt directly to answer. "Reasoning" happens implicitly in the forward pass weights. No explicit search, backtracking, or self-verification.
  • GPT-4 (non-o1): prompt → answer immediately
  • Cannot recover from a bad first step
  • Chain-of-thought helps but is not systematic
  • More parameters → better reasoning (scaling law)
  • Fixed compute regardless of problem difficulty
Input: "Prove that √2 is irrational" Model: [one forward pass] Output: "Assume √2 = p/q... therefore irrational." Time: ~0.5s | Tokens: ~200 | No self-check
Modern
Reasoning Model (o1/o3/R1/QwQ)
Model generates a long chain-of-thought "thinking" block before the answer. Trained with RL to search, verify, and backtrack. More compute = better answer.
  • o3-mini: reasoning_effort low/med/high
  • Claude 3.7: budget_tokens up to 100K
  • DeepSeek-R1: open-source, full thinking trace
  • Test-time compute scales as a new dimension
  • Solves AMC/AIME/Olympiad problems
Input: "Prove that √2 is irrational" <thinking> Let me assume √2 = p/q in lowest terms... Then 2q² = p², so p² is even, so p is even... Write p = 2k, then 2q² = 4k², q² = 2k²... So q is also even — contradiction with lowest terms. Wait, should I also show the general case? Let me verify... </thinking> Output: Clean proof Time: 15-60s | Think tokens: 2000-50000
TaskGPT-4 Turboo3 (high)
AIME 2024 math13%96%
SWE-bench coding7%49%
PhD-level science (GPQA)36%87%
Response latency0.5-2s10-120s
Cost per query$0.01$0.20-$2.00
Simple Q&A tasksExcellent valueOverkill
Use Standard LLM When
  • Summarisation, classification, extraction
  • Conversational chat, customer support
  • Low-latency requirements (<2s)
  • High-volume, cost-sensitive workloads
Use Reasoning Models When
  • Complex math / proof / algorithm design
  • Multi-step code generation (SWE tasks)
  • Scientific research, data analysis
  • High-stakes decisions where quality > cost
Bottom line: Reasoning models are a paradigm shift — they move intelligence from training-time scale to inference-time search. For hard problems, they're worth the cost. For everyday tasks, standard models remain better value by 10-100×.
💡 Simple: Standard models are fast and cheap — right tool for summarisation, Q&A, and classification. Reasoning models spend 10–120 seconds generating an internal thinking chain before answering — overkill for simple tasks but transformative for math, complex code, and science (o3 scores 96% on AIME vs GPT-4's 13%). Pick based on task complexity.

Naive RAG vs Advanced RAG
Retrieval quality evolution
Fixed chunks + cosine similarity VS Hybrid retrieval + reranking + query expansion
Naive RAG (2023)
Fixed Chunk Embedding Search
Split document into 512-token chunks. Embed all chunks. At query time, embed query, find top-k by cosine similarity, stuff into prompt.
  • Chunks split mid-sentence → broken context
  • Semantic search misses keyword matches
  • No query expansion for ambiguous questions
  • Top-k by similarity ≠ most relevant
  • "Lost in the middle" — LLM ignores middle docs
Docs → fixed 512-token chunks → embeddings → vector store Query → embed → cosine top-5 → stuff into prompt → LLM
Advanced RAG (2024–25)
Hybrid + Rerank + Multi-Query
Semantic + keyword (BM25) hybrid retrieval. Query expansion generates multiple sub-queries. Reranker re-scores candidates. Contextual chunking preserves meaning.
  • Semantic + BM25 → both fuzzy and exact matches
  • HyDE: generate hypothetical answer, embed that
  • Multi-query: expand "X" to 3 sub-questions
  • Cross-encoder reranker rescores top-50 → top-5
  • Parent-child chunking: retrieve child, return parent
Docs → contextual chunks + summaries → vector + BM25 index Query → LLM expands to 3 sub-queries All sub-queries → hybrid retrieve top-50 → deduplicate Top-50 → cross-encoder reranker → top-5 Top-5 + query → LLM answer + citations
TechniqueNaive RAGAdvanced RAG
Faithfulness (no hallucination)60-70%85-92%
Answer relevance55-65%80-90%
Latency0.5-1s retrieval1-3s (reranker adds ~0.5s)
Infra complexityJust vector storeVector + BM25 + reranker
Handles typos/abbreviationsPoorGood (BM25 handles)
Cross-document reasoningPoorGood (graph RAG / fusion)
Bottom line: For production RAG, always add BM25 hybrid and a cross-encoder reranker — both are easy to add and produce 15-25% quality improvement. Query expansion helps on ambiguous short queries. GraphRAG adds another 10-20% on multi-hop questions.
💡 Simple: Naive RAG: embed chunks, find closest by cosine, pass to LLM. Advanced RAG adds three things: BM25 keyword matching alongside semantic search (catches exact-match queries), query expansion to handle ambiguous questions, and a cross-encoder reranker to rescore the top 50 candidates. These additions give 15–25% quality improvement at modest latency cost.

Full Fine-tuning vs LoRA / QLoRA
Efficient adaptation of large models
Update all 7B parameters VS Update 0.1% with low-rank adapters
Traditional
Full Fine-Tuning
Every weight in the model is updated during training. Requires storing all gradients and optimiser states — 3-4× model size in VRAM.
  • 7B model: ~28 GB weights + ~112 GB gradients+Adam
  • Requires A100 80GB or multi-GPU cluster
  • Risk of catastrophic forgetting
  • A separate checkpoint per fine-tuned use case
  • Merge/serve = deploy entire new model
7B model: 7,000,000,000 trainable parameters VRAM = 14 GB (fp16 weights) + 28 GB (fp16 gradients) + 56 GB (Adam states: m, v per param) = ~98 GB minimum → 8× A100 needed
Modern
QLoRA (4-bit + LoRA)
Base model quantised to 4-bit (frozen). Tiny low-rank adapter matrices (A, B) are trained in fp16. Only adapter weights have gradients.
  • 7B model: ~4 GB (4-bit NF4) + ~20-40 MB adapters
  • Trainable on a single 16GB RTX 4080!
  • Base model preserved — swap adapters per task
  • LoRA rank r=16 → 0.05% of total params trained
  • Near full fine-tune quality on domain adaptation
W = W₀(frozen 4-bit) + α/r × (A · B) [LoRA] ↑ only A and B are trained A ∈ R^{d×r}, B ∈ R^{r×k}, r=16 (vs d=4096, k=4096) Trainable: 2 × 4096 × 16 = 131,072 params (per layer) vs Full FT: 4096 × 4096 = 16,777,216 params (per layer) Reduction: 128× fewer trainable params!
MetricFull Fine-TuningQLoRA (r=16)
VRAM (7B model)~98 GB~10 GB
Trainable params7B (100%)~7M (0.1%)
Training time (1K examples)4-8 hours (8×A100)30-60 min (1×RTX 4090)
Quality vs full FT100% (reference)95-99%

Catastrophic forgettingHigh riskLow (base frozen)
Bottom line: QLoRA democratised fine-tuning — anyone with a consumer GPU can adapt a 7B or even 13B model. Full fine-tuning is still preferred for instruction tuning from scratch and multi-task training where you need maximum capacity.
💡 Simple: Full fine-tuning updates all 7B parameters and needs ~98GB VRAM — an 8-GPU cluster. QLoRA freezes the base model in 4-bit and trains only tiny adapter matrices (~20MB total) that fit in a single 16GB consumer GPU. Near-identical quality. Full fine-tuning is only worth the hardware cost when you need absolute maximum capacity.

RLHF (PPO) vs DPO vs GRPO / RLVR
Alignment training evolution
PPO + reward model (2022) → DPO (2023) → GRPO / RLVR (2024)
Generation 1 (2022)
RLHF with PPO
Four models in memory simultaneously: policy (LLM), reference policy, reward model, value model. Complex training loop with PPO clipping.
  • Requires human preference data → reward model training
  • 4 model copies in VRAM during training
  • PPO is notoriously unstable (reward hacking)
  • Separate SFT → RM training → PPO training stages
  • Used by: InstructGPT, ChatGPT, original Claude
Stage 1: SFT — fine-tune on demonstrations Stage 2: RM — train reward model on (chosen, rejected) pairs human rates: "response A better than B" × 10K+ examples Stage 3: PPO — RL loop: policy_model.generate() → reward_model.score() → PPO update (with KL penalty vs reference model) 4 models in VRAM: policy + ref + reward + value
Generation 2-3 (2023–24)
DPO → GRPO / RLVR
DPO eliminates the reward model — directly optimises preference pairs with a closed-form loss. GRPO groups multiple samples and uses relative reward, avoiding value model.
  • DPO: just policy + reference (2 models). Stable.
  • GRPO: generate G samples, score, normalise rewards
  • RLVR: verifiable rewards (math = checkable answer)
  • DeepSeek-R1 trained entirely with GRPO on math
  • No reward hacking — rewards are verifiable facts
DPO loss: -log σ(β·[log π_θ(y_w|x) - log π_ref(y_w|x)] - log π_θ(y_l|x) + log π_ref(y_l|x)]) No reward model needed — just (chosen, rejected) pairs! GRPO: generate G=8 responses per prompt rewards r₁..r₈ = verify(answer) → 0 or 1 advantage = (rᵢ - mean(r)) / std(r) update policy to maximise advantage
MethodModels in VRAMStabilityData neededBest for
PPO (RLHF)4 (policy+ref+RM+value)Low (reward hack)Human rankings (expensive)General helpfulness
DPO2 (policy+ref)High (supervised)Preference pairsStyle / safety alignment
GRPO / RLVR1-2 (policy+ref)Very highProblems with verifiable answersMath / code / reasoning
Bottom line: PPO is still used by frontier labs (GPT-4, Claude 3) for general alignment. DPO is the go-to for open-source fine-tuning. GRPO/RLVR is the breakthrough technique that created DeepSeek-R1's reasoning capability — works only when you can automatically verify answers.
💡 Simple: PPO-RLHF needs 4 models in VRAM simultaneously and is notoriously prone to reward hacking. DPO reformulates alignment as a simple supervised loss — just 2 models, stable, and widely used for open-source fine-tuning. GRPO uses verifiable rewards (correct math answer = +1, wrong = 0) — no reward model, no value model, created DeepSeek-R1. Use DPO for style/safety; GRPO when answers are checkable.

Large Foundation Models vs Small Language Models (SLMs)
The right-sizing revolution
GPT-4 class (100B+ params) VS Phi-3.5 / Qwen2.5 / Llama-3.2 (1-4B)
Traditional Assumption (2022)
Bigger is Always Better
GPT-3 showed scale = capability. The assumption: intelligent behaviour requires massive models. Small models can't follow instructions, reason, or be reliable.
  • GPT-3: 175B, needs 8× A100 to run
  • $0.02-0.06 per 1K tokens API cost
  • 100-500ms latency per response
  • Cannot run on mobile / edge devices
  • Privacy concern — data leaves device/org
175B model: VRAM: 350 GB (fp16) → 8× A100 80GB Cost: $0.06/1K tokens (GPT-3.5 Turbo, 2022) Speed: ~60 tokens/s on 8× A100 Mobile: impossible

SLMs — Distilled, Curated, Efficient
Phi-3.5 Mini (3.8B) achieves GPT-3.5 level quality by training on extremely curated "textbook quality" data. Runs on phone. Quantised models on browser.

Standard Attention vs FlashAttention / Sliding Window
Memory-efficient attention implementations
Full O(n²) attention matrix in HBM VS IO-aware tiling / local window
Standard Attention
Full Materialised Attention Matrix
Computes and stores the full n×n attention matrix in GPU HBM (slow memory). Multiple reads/writes to HBM for softmax, dropout, masking.
  • Memory: O(n²) for attention matrix
  • Attention matrix stored in HBM (slow)
  • Multiple passes: QKᵀ, softmax, ×V, each one HBM r/w
  • Context limit: 2K-4K tokens (2022)
  • Most time is memory bandwidth, not compute
HBM (slow, 900 GB/s): Write: QKᵀ matrix (n×n floats) ← bottleneck Read: for softmax normalization Write: softmax(QKᵀ/√d) matrix Read: × V matrix Write: output SRAM (fast, 19 TB/s): only small register operations
FlashAttention 2/3
Tiled IO-Aware Attention
Divides Q, K, V into blocks. Computes attention tile-by-tile entirely in fast SRAM. Never materialises the full n×n matrix in HBM.
  • Memory: O(n) — only output is stored in HBM
  • Tiling: process blocks entirely in SRAM (fast)
  • Online softmax: maintains running max/sum
  • 2-4× faster than standard PyTorch attention
  • Enables 32K-128K context without OOM
SRAM (fast, tile-level only): Load tile Q_i, K_j, V_j → compute partial attention Update running softmax stats (online algorithm) Accumulate output O_i incrementally HBM reads: O(n·d) ← just the matrices, not n×n matrix HBM writes: O(n·d) ← just the final output Memory: O(n) vs O(n²) — 16K ctx = 1000× less HBM traffic!

Bottom line: FlashAttention is now the default in all serious LLM training/inference stacks (vLLM, TGI, llama.cpp). It produces mathematically identical results to standard attention but 2-4× faster with 64-1000× less HBM memory. Use torch.nn.functional.scaled_dot_product_attention — it auto-selects FlashAttention when available.
💡 Simple: FlashAttention does not change what attention computes — it changes where the computation happens. By tiling and keeping intermediate values in fast SRAM instead of writing them to slow HBM, it achieves the same result 2–4× faster with 64–1000× less memory traffic at long contexts. It is a free performance upgrade — just use PyTorch's built-in scaled_dot_product_attention.

│   └── Knowledge base / document Q&A                     → Advanced RAG (hybrid + reranker)
│
├── Scale / parameter efficiency
│   ├── Want more capacity without more compute            → MoE (Mixtral, DeepSeek)
│   ├── Adaptive per-token compute (research)              → MoR (future)
│   └── Alignment / instruction tuning on budget          → DPO or GRPO (if verifiable)
│
└── Deployment constraint
    ├── On-device (mobile, browser, offline)               → SLM + Transformers.js / llama.cpp
    ├── Privacy (data cannot leave device)                 → Local SLM (Phi-3.5, Llama-3.2)
    └── Fine-tune on limited GPU (<16GB)                  → QLoRA (4-bit + adapters)
💡 Simple: Use this tree whenever you are choosing an approach: high-volume + well-defined task → fine-tuned SLM; needs external or current knowledge → RAG; needs hard reasoning (math/code) → reasoning model; need more capacity without more compute → MoE; inference speed is the bottleneck → speculative decoding or FlashAttention. No single approach wins across all dimensions.
